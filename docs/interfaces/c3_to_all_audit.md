# 接口契约：AI-C3 → 所有开发 Agent（安全审计）

**状态：ACTIVE（本契约随仓库初始化即生效）**
**维护：AI-00｜所有者：AI-C3**

> **任何网络代码未通过 AI-C3 审计，不得合并。**
> AI-C3 拥有一票否决权，AI-00 不得推翻。

---

## 1. 审计请求

开发 Agent 在以下情况下**必须**发起审计请求：

| 触发 | 时机 |
|---|---|
| 设计审计 | 实现网络功能**之前**（提交设计说明） |
| 代码审计 | PR 合并**之前** |
| 密码学审计 | 涉及加解密 / 密钥 / 随机数 / 哈希 |
| 隐私审计 | 涉及任何标识、存储、出网字段 |
| 持续审计 | 每次网络代码变更 |

发起方式：使用 `.github/ISSUE_TEMPLATE/security-audit.yml` 建立 Issue，并打 `security` 标签。

---

## 2. 审计结果

```text
PASS                 通过，可以合并
PASS_WITH_WARNING    通过，但警告项必须建 Issue 跟踪
FAIL                 一票否决，阻断合并
```

**结果传递约定**

- 结论以**审计报告**为准，存放在 `docs/audit/`；
- PR 必须打上对应标签：`audit:passed` / `audit:warning` / `audit:failed`；
- `audit:failed` 的 PR 由 CI 阻断（见 `.github/workflows/pr-guard.yml`）。

---

## 3. 审计报告结构

见 [`../audit/README.md`](../audit/README.md) §3。

报告必须**可追溯**：每条检查项对应到具体的文件与行号，不接受“已检查”这类无证据结论。

---

## 4. 争议处理

若开发方认为审计结论有误：

```text
1. 在 docs/conflict_log/ 建立冲突记录（CONFLICT-<日期>-<序号>）
2. 提交证据（反汇编 / 测试 / 规范引用）
3. 由 AI-C2 裁决（安全优先）
4. 裁决完成前，保持阻断
```

**允许**推翻 `FAIL` 的唯一路径是上述流程给出的书面裁决，且必须说明安全影响的处理方式。

---

## 5. 检查项基线

任何网络相关 PR 至少要回答：

- [ ] 是否新增了出网字段？是否包含隐私数据？
- [ ] 是否新增了持久化标识？
- [ ] 消息是否附带 HMAC 与单调递增序列号？
- [ ] 时间戳防重放窗口是多少？与 500ms 延迟阈值是否兼容？
- [ ] 会话密钥是否定期轮换？私钥是否只存内存？
- [ ] 校验失败路径是否会记录 `[SECURITY]` 日志并拒绝？
- [ ] 中继是否仍无法解密 / 篡改 / 重放 / 记录日志？
- [ ] 速率限制与包大小上限是否覆盖新消息类型？
- [ ] 版本握手是否强校验，不一致是否拒绝连接？
- [ ] 存档写入是否原子化？非法物品是否被拒绝写入？
- [ ] 物品发放是否有记账，唯一物品是否防重复？
