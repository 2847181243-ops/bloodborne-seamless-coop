  缺 `charset=utf-8` 会得到 **404**（不是 415），极难排查。

### 3.2 本地预检

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\preci\preci.ps1 -Stage 1 -AllowSkip
```

- **基于 `develop` 的 `task/*` 分支必须加 `-Base origin/develop`**，否则默认对
  `origin/main` 做三点 diff，会报出一堆幽灵越界文件（曾报 33 个）。
- **`preci.ps1` 带 UTF-8 BOM。** 用编辑工具改它会**剥掉 BOM**，
  然后 PowerShell 5.1 按 GBK 读 → 中文乱码 → ParserError 指向一行看起来正常的代码。
  改完必须加回：`open(p,'wb').write(b'\xef\xbb\xbf' + raw)`。
  有套件盯着：`test_ps1_bom.py`。
- **`check_style.py` 只看 HEAD 里的内容**（`git ls-tree HEAD` + `git cat-file`），
  **既不是索引、也不是工作树**。
  ⚠️ 「先 `git add` 再跑」的说法是**错的** —— `git add` 不会让它看到改动，
  **必须先 commit**。这一条是实测纠正的。
- **回归矩阵自己也会踩「没传 `-Base`」的坑，而且必然踩。**
  `tools/preci/tests/test_skip_reason.py` 直接跑 `preci.ps1 -Stage 1`（不传 `-Base`），
  于是对 `origin/main` 做三点 diff，把 `docs/security/*`（8 个）与 `LICENSE` 这些
  **早就存在的旧文件**算成越界 → 退出码 1 → 该套件 5/7，整套矩阵 16 项里红 1 项。
  这是**误报**，不是你的改动越界；在基于 `develop` 的 `task/*` 分支上 100% 复现。
  已建 Issue #64。**不要为了让矩阵变绿去改自己的写入范围** —— 那是把误报变成真问题。
- **跑矩阵/runci 前先设 `PYTHONUTF8=1` 与 `PYTHONIOENCODING=utf-8`**，否则子进程按 GBK 输出，
  日志里全是乱码，等于没有日志。

### 3.3 编译

本机**没有 MSVC，cmake 也不在 PATH**。但 `tools/toolchain/pylibs/` 下有可用的：

```powershell
$cmake = "tools\toolchain\pylibs\cmake\data\bin\cmake.exe"
$cxx   = "tools\toolchain\zig-cxx.cmd"     # 包装 zig 当 C++ 编译器
$ar    = "tools\toolchain\zig-ar.cmd"      # 必需，见下

& $cmake -S . -B build -G Ninja `
    "-DCMAKE_CXX_COMPILER=$cxx" `
    "-DCMAKE_AR=$ar" "-DCMAKE_RANLIB=$ar"
& $cmake --build build
```

⚠️ **`-DCMAKE_AR` 与 `-DCMAKE_RANLIB` 不能省。** 只给 `CMAKE_CXX_COMPILER` 的话，
第一个静态库就会失败：`'CMAKE_AR-NOTFOUND' is not recognized...`。
（`docs/standards/build-standards.md` §1 记了这个坑，我是漏在本文里的。）

⚠️ **不要传 `-DCMAKE_C_COMPILER`** —— 根 `CMakeLists.txt` 只声明了 `LANGUAGES CXX`，
传了会得到 unused-cli 警告。

- **zig 的 `c++` 驱动不支持 `-fsyntax-only`** —— 它报 `error: FileNotFound`
  并指向**源文件**，让人去找一个根本没丢的文件。用 `-c -o`。
- **`alignas` 会踩 MSVC 的 C4324（级别 4）。** 本仓库是 `/W4 /WX`，所以给结构体加
  对齐说明符（含 `alignas(64)` 做缓存行隔离）会**直接让 CI 构建门禁变红**，
  而本机没有 MSVC，测不出来。没有实测数据之前不要加对齐说明符（见
  `src/ipc/include/bbcoop/ipc/ring_buffer.h` 的注释）。
- **`GetModuleFileNameW` 返回 0 判断用 `!= 0`**：`> 0` 是 unsigned 与 int 比较
  （C4018 级别 3），在 `/WX` 下同样致命。
- **`python` 可能解析到 Microsoft Store 的 0 字节应用执行别名**
  （`%LOCALAPPDATA%\Microsoft\WindowsApps\python.exe`）。
  交互式能跑，**非交互 + 重定向输出时失败**：`The file cannot be accessed by the system`。
  `preci.ps1` 的 `Resolve-Python` 会跳过它。

### 3.3.1 加新模块时的两个坑（实测）

- **根 `CMakeLists.txt` 第 146 行附近有一行注释掉的**
  `#     add_subdirectory(src/modules/transport)`。
  机械地把 `add_subdirectory(src/modules/transport)` 替换成「两行」时，
  **会在注释里也插一行**，于是 discovery 被 `add_subdirectory` 两次，报：
  `The binary directory ... is already used to build a source directory`。
  **谁去加第三个模块都会踩。**
- **`bbcoop_add_module()` 应该把目标名回吐给调用方**
  （`set(BBCOOP_MODULE_TARGET <target> PARENT_SCOPE)`）。
  否则模块自己的 `CMakeLists.txt` 里要写死
  `set(_transport_module_target bbcoop_mod_transport)` ——
  复制成 discovery 时不改这行就会链到 transport。已记入 T-009 的验收。

### 3.4 git

- **三点 diff 噪声**：分支基于 `develop` 但 PR 提给 `main` 时，
  两个提交的**树相同、历史不同**，GitHub 会按旧 merge-base 算出大量幽灵文件
  （曾把一个 5 文件的 PR 显示成 38 个）。
  **修法**：把分支重建到目标分支上（`git checkout -B <branch> origin/main` + `cherry-pick`）。
- **`git show <ref>:<file> > out` 在 PowerShell 里写的是 UTF-16LE**，
  捕获到的文件以 `ff fe` 开头，看起来像有 BOM。**用 `git cat-file blob`**。
- 提交信息里不能用 `#` 开头（会被当注释）：`-c core.commentChar=';'`。
- **develop 有独有提交时不要用 `sync/*`**：sync 的前提是「树 == main」，
  树重置会把 develop 上的任务产出整个清掉。改用「从 develop 切分支、合并 main」的 PR
  （实测见 Issue #60 / PR #62）；判据：`git diff origin/develop...HEAD` 只包含 main 的独有提交。
- **换行处理陷阱**：读一个 CRLF 文件后用 `newline='\r\n'` 写出，会把已有的 `\r\n`
  变成 `\r\r\n`；git 会把这种混合换行的文件判成二进制（`w/-text`）并跳过归一化，
  随后 style 门禁报「CRLF in a file declared LF」。统一按仓库约定落 LF（BOM 按原样保留）。
- **不要用 PowerShell 5.1 的 `Get-Content` / `Set-Content` 改仓库里的 UTF-8 源文件。**
  `Get-Content -Raw` 按**系统代码页（GBK）**读，中文注释立刻变乱码；`Set-Content` 再按
  同一代码页写回，于是：① 注释永久损坏；② 乱码里出现的字符会**打破 C++ 语法**
  （实测报 `function definition is not allowed here`，而报错行看起来完全正常）。
  本机 `pwsh` 是 5.1（`$PSVersionTable.PSVersion` = 5.1.26100），不是 PowerShell 7。
  **改文件用编辑工具（按 UTF-8 读写），或 Python 里显式 `encoding='utf-8'`。**
- **「构建失败 + 跑了旧二进制 = 假通过」。** 用脚本做破坏性反向验证时，如果编辑手段本身
  弄坏了源文件，编译会失败，而**旧的可执行文件照跑照过** —— 负例"通过"了，其实什么都没验。
  做反向验证时必须：① 显式检查构建退出码（不要 `| Out-Null`）；② 确认可执行文件哈希变了；
  ③ 负例必须**真的变红**。
- **提交前必须核对 `git status --porcelain` 的文件数与预期一致。**
  `git add -A` 在有**未跟踪**文件时很危险 —— 本仓库已经因此出过两次事故：
  一次差点把 `second.md` 提交，一次把助手写在未跟踪状态的 28 个文件
  扫进了提交（预检报 28 个文件越界）。
  **养成提交前数一遍的习惯**，`git add -A` 只在你确认过清单时才用。

## 4. 门禁机制（改动前先看这里，避免白跑一轮 CI）

### 4.1 规则集

| 名称 | id | 作用于 |
|---|---|---|
| `main-protection` | 24735428 | `refs/heads/main` |
| `develop-protection` | 24804847 | `refs/heads/develop` |

两者都是：6 个必需检查 + `strict=true` + 线性历史 + squash-only + 审批数 0。

**6 个必需检查的名字**（必须逐字一致）：
```
必需文件与目录结构 / 分支命名与写入范围 / PR 模板必填章节 /
安全审计门禁（一票否决） / 文件编码与 CODEOWNERS 完整性 / 构建门禁（Windows MSVC x64）
```

### 4.2 写入范围（SCOPE）

`branch-policy.yml` 里按分支类型映射：

| 分支 | 范围 |
|---|---|
| `lead/*` | `.github/` `.dsh/` `tools/preci/` `docs/standards/` `docs/interfaces/` `bloodborne.markdown` `README.md` `CONTRIBUTING.md` `SECURITY.md` `MAINTAINERS.md` `AI_POLICY.md` `CMakeLists.txt` 等 |
| `task/*` `fix/*` | 联合范围（含 `src/` `tests/` `config/` `docs/architecture/` `docs/modules/` `scripts/` `reports/`）。**这是迁移期的临时范围，不是最终模块所有权** |
| `sync/*` | 不走范围检查，但**必须验证树与 main 完全一致** |

### 4.3 PR 描述

必需章节 8 个：`改了什么` `为什么改` `修改了哪个模块` `影响哪些系统` `如何验证`
`是否存在兼容性风险` `当前验证等级` `决策与不确定记录`。

另需 `- 关联 Issue：#<数字>`（真实编号，CI 会核对该 Issue 存在）。

**验证等级必须且只能勾 1 个**（任务书 §39 不允许跳级或并列声明）。

### 4.4 已知的非必需检查

`github-advanced-security` 是 GitHub 自动挂的托管代理（`dynamic/agents/...`），
**不在我们的规则集里**。它因 Copilot 月度配额失败过，
`mergeable_state` 仍为 `clean` —— 不代表门禁出问题。
