# 重构对照：保留什么、重建什么

> **用途**：v2.0 要把仓库重构成 `src/` + Kernel/模块结构并换掉分支流程。
> 这份文件回答一个问题：**现有资产里哪些能直接带过去，哪些要改，哪些要重做。**
>
> 结论先行：**基础设施大约 85% 可保留；文档约 70%；功能划分要重做。**
> 现有仓库是"有治理、无实现"的纯文档仓库（`mod/`、`src/` 都不存在），
> 所以这次重构**不是拆房子重建，是给空房子换户型图**。

## 二、工程流程与门禁：约 85% 可保留

### 2.1 七个 workflow 的处置

| workflow | 作用 | 处置 | 要改什么 |
|---|---|---|---|
| `pr-guard.yml`（661 行） | PR 描述 7 章节 + 机器可验证项 + 审计证据 + 聚合 `gate` | **保留** | 改触及路径（`mod/` → `src/modules/`）；改 Issue 关联要求 |
| `branch-policy.yml`（179 行） | 分支命名 + 写入范围 + 跨所有权授权 | **保留，重写 SCOPE** | `agent/a0..c4` → `task/T-xxx-*`；SCOPE 换成模块路径 |
| `repo-integrity.yml`（160 行） | 编码 + CODEOWNERS 完整性 | **保留，原样** | CODEOWNERS 条目要跟着模块改 |
| `docs-structure.yml`（113 行） | 必需文件与目录 | **保留，换清单** | `required` 数组换成 v2.0 §七 的交付物 |
| `build.yml`（99 行） | MSVC x64 构建门禁 | **保留，扩展** | 单 target → 多 target + 模块隔离构建 |
| `labels.yml`（52 行） | 标签同步 | **保留，原样** | — |
| `issue-triage.yml`（89 行） | Issue 自动标注 | **保留，加模板** | 加 `module_task` / `layer_gate` / `fault_injection` |

**一个必须保留的设计**：`pr-guard.yml` 的 `gate` 是**单一聚合必需检查**。
它解决了"job 被 `if:` 跳过会报 Success"与"workflow 被过滤会永远 Pending"两个坑。
v2.0 要新加 5 个 CI workflow（T-012），**必须沿用这个模式**，
否则规则集会有一堆永远 Pending 的必需检查。

### 2.2 `tools/preci/` —— 几乎原样保留

| 资产 | 处置 |
|---|---|
| `preci.ps1`（32 KB，10 项检查） | **保留**。检查项与模块划分无关 |
| `tests/`（11 个套件） | **保留**。它们验证的是门禁本身 |
| `gates.yml` | **改**：必需检查清单要加 v2.0 的 5 个 CI workflow |
| `check_style.py` | **扩展**：加"模块间非法 `#include`"检查（对应 §1.3 硬禁止） |
| `messages.json` | **保留**；新增消息加键 |
| `README.md` | **改**：说明新流程 |

**为什么这是最有价值的部分**：它已经带着"检查失效时会被发现"的设计 ——
11 个负例矩阵会验证门禁仍然拦得住东西。v2.0 的 T-012 要从零建 5 个 CI workflow，
**直接复用这套而不是重写，能省掉重新踩一遍坑。**

### 2.3 `tools/bbcoop.py`

**保留，加子命令**。现在有 `check` / `test` / `verify` / `doctor` / `status`。
v2.0 需要的 `self-test` / `fault-injection` / `module-isolation` 可以加成子命令，
而不是各写一个脚本 —— 单一入口的价值就在这里。

### 2.4 退出码约定

**必须保留并推广到新脚本**：

```text
0 = 通过
1 = 有失败
2 = 有未验证项（跳过）—— 不等于通过
3 = 无法启动
```

v2.0 的 `--self-test` 要求"required 失败退出码非 0"，
用这套约定可以直接对齐：**required 失败 = 1，optional 跳过 = 2**。

## 三、文档：约 70% 可保留

### 3.1 `docs/security/` —— 直接对应 Layer 0

这是**可保留度最高的部分**，因为 Layer 0 的五个模块恰好覆盖了已写好的安全设计：

| 现有文档 | 对应模块 | 处置 |
|---|---|---|
| `threat_model.md`（14 KB） | 全局 | **保留** |
| `security_architecture.md`（12 KB） | 全局 | **保留** |
| `key_exchange.md` | `mod.crypto` | **保留** |
| `relay_security.md` | `mod.relay` | **保留** |
| `constraints.md`（19 KB，C-001…C-019） | `mod.transport`/`discovery`/`relay` | **保留**，但**要求改两级标注的后果分级**（见交接文档） |
| `anti_sybil.md` | `mod.discovery` / `mod.session_core` | **保留** |
| `anti_ddos.md` | `mod.transport` / `mod.relay` | **保留** |
| `privacy.md` | 全局 | **保留** |

**关键**：`constraints.md` 的 C-001…C-019 与 v2.0 §1.3 的硬禁止**几乎一一对应** ——

| v2.0 硬禁止 | 现有约束 |
|---|---|
| 不降级加密为明文 | `C-001` 端到端加密强制 |
| 中继不能解密/篡改/重放 | `C-002` 中继零信任 + `C-011` |
| 不提交密钥凭据 | `SECURITY.md` §9 |
| 反作弊失败仅禁用 PvP | `C-012` 反作弊仅限 PvP |

**所以 §1.3 不需要新写一套，只需要在约束表里标注对应关系。**

### 3.2 `docs/interfaces/` —— 内容有效，命名要改

7 份接口契约的内容（事件、状态、E2EE、审计）**依然有效**，
但文件名依赖旧的 Agent 编号：

```text
a1_to_a2_events.md            → 建议 mod.game_hook → mod.replication_core
a2_to_a3_a4_state.md          → 建议 mod.replication_core → mod.death / mod.loot
b3_to_b4_reputation.md        → 建议 mod.session_core → mod.relay
c1_to_b1_b4_e2ee.md           → 建议 mod.crypto → mod.transport / mod.relay
c2_to_b_security_constraints.md → 建议 security → Layer 0 全体
c3_to_all_audit.md            → 建议 mod.security_audit → 全体
```

⚠️ **重命名不是机械替换**：旧划分把"session 与复制"合成一个 Agent（a2），
v2.0 把它们拆成 `mod.session_core`（Layer 0）与 `mod.replication_core`（Layer 1）。
**跨层的接口要重新确定方向** —— 这正是 §二 第 3 条"接口通信"要冻结的东西。

### 3.3 `docs/standards/` —— 全部保留

|---|---|
| `build-standards.md` | **保留**；补多 target 的编译标准 |
| `bypass-and-gates.md` | **保留**；这是"绕过手段 × 捕获者"的对照表 |
| `stop-loss-rules.md` | **保留**；v2.0 长任务多，这条更必要了 |
| `参考-build_in_harmonyos-可复用经验.md` | **保留**；T-000 与 T-012 直接参考 |

### 3.4 任务书 v1.0 里**最有价值、最不可重做**的部分

这是我最想强调的一点：**任务书里的游戏机制设计是花了几百行推导出来的，
v2.0 完全没有覆盖它，而它恰恰是最难重做的。**

| 任务书位置 | 内容 | 为什么必须保留 |
|---|---|---|
| 死亡经济 | Blood Echoes 掉落/回收/再次死亡；World Reset 是否清地面掉落 | 每一条都是"错了就写出相反逻辑"，且需要逆向验证 |
| 死亡惩罚 | 死亡玩家自身 Max HP 降低、可叠加、最低 30%、仅 Lantern Rest 清除 | 数值与触发条件都在 |
| Scaling 独立性 | **玩家死亡次数绝不能让敌人/Boss 的 HP 增加** | 容易被"动态难度"的想法破坏 |
| 世界重置分层 | 死亡是 Player-Level；Lantern / Party Wipe 才是 World-Level | 单人死亡不触发重置 |
| 物品与掉落 | 掉落归属、固定拾取多人行为、Boss 掉落分配、唯一性标志 | 对应 `mod.loot` |
| 防复制 | 消耗品复制、商店购买复制、无限重生、敌人无限重置 | 对应 `mod.loot` / `mod.save` |
| 存档 | 客机临时使用主机世界状态（仅内存不写存档）、`.bloodco` | 对应 `mod.save`；写错会**存档损坏** |
| PvP / 反作弊 | 单人死亡不是结算点、整队全灭才结算；反作弊仅限 PvP | 对应 `mod.pvp` |
| 决斗场 | 仅 1v1、必须主动离开 Session、房主不得携带客机进入 | 对应 `mod.pvp` |
| NPC | 友好 NPC 识别、伤害判定、敌对触发 | 对应 `mod.enemy_boss` |

**v2.0 的 15 个模块只规定了"边界与故障隔离"，没有规定"每个模块内部该做什么"。**
这些设计必须从 v1.0 搬过去，否则 T-010（模块任务书 ×15）会写成空壳。

**建议**：T-010 的 `docs/modules/<module>.md` **必须包含**
"本模块的原版行为约束"，内容直接取自 v1.0 对应章节，并标注出处行号。

## 四、要重建的部分

| 项 | 原因 | 工作量 |
|---|---|---|
| **分支与所有权模型** | `agent/a0..c4` → `task/T-xxx-*`；`main` → `develop`；15 个模块路径 | T-000 + T-019 |
| **`src/` 目录结构** | 目前不存在，全新 | T-003 |
| **15 个模块骨架** | 不存在 | T-007 |
| **Kernel 与接口层** | 不存在 | T-004 / T-005 / T-006 |
| **配置系统** | `config/modules.yaml` 等不存在 | T-008 |
| **CMake 多 target** | 现在只有一个接口目标 `bbcoop_warnings` | T-009 |
| **5 个新 CI workflow** | 单元/契约/故障注入/模块隔离 | T-012 |
| **故障注入套件** | 不存在 | T-013 |
| **`--self-test`** | 不存在 | T-014 |
| **发布打包** | 不存在 | T-015 |

### 一个必须先决策的冲突

v2.0 §1.2 的权限矩阵要求：

```text
合并到 main             → ❌ 需批准
修改 crypto/auth/反作弊 → ❌ 需 Security Reviewer + Owner
```

**但这是个人账号仓库、CODEOWNERS 单账号。** GitHub 不允许自审，
`required_approving_review_count ≥ 1` 会让唯一账号无法合并自己的 PR。

这条不解决，T-000 的验收条件（"Human Owner 可据此配置分支保护"）达不到。
三个可选出路见 `docs/standards/参考-build_in_harmonyos-可复用经验.md` 与
`docs/audit/README.md` 的说明。**建议：承认它是"文本层强制"，
并把这一点写进 `MAINTAINERS.md`，而不是声称平台级保证。**

## 五、建议的重构顺序（与 v2.0 的差异）

v2.0 的顺序是 `T-000 → T-001 → T-002 → T-003 → …`。我建议**微调**：

```text
1. 先解决 3 个阻塞项（权限多签、develop 决策、旧分支清理）
2. T-002 前先确认章节编号规则（已写入 second.md「四之二」）
3. T-000 复用现有治理，不重写
4. T-003 前先做「旧资产映射」（本文件），避免重写已有的东西
5. T-012 复用 preci 的聚合 gate 模式与退出码约定
6. T-010 必须搬入 v1.0 的游戏机制设计
```

**第 4 步是我最想强调的**：v2.0 的 20 个任务卡里没有任何一个说
"先盘点现有资产"。如果直接按顺序执行，会出现
"重新发明已经有的门禁"和"丢失已经推导好的游戏机制"两种浪费。

---

## 六、一句话结论

**这次重构的难点不在"写新代码"，在两件事：**

1. **把已经写好的安全设计与游戏机制正确映射到 15 个模块上** —— 映射错了，后面全错
2. **不要重写已经能用的工程门禁** —— 它已经带着"失效时会被发现"的自检
