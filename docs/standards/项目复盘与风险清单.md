## 3. 最终目标可行性评估

### 3.1 支持面（说明"不是不可能"）
- **同生态先例**：`yuiamoroll` 系列 Seamless Coop Mod（Elden Ring 1601 stars；DS1 / DS2 / DS3 / Sekiro / Nightreign），证明"无缝联机"在官方 PC 版 Souls 游戏上可行。
  （仅确认仓库存在与 star 数，未读实现 —— 证据等级：外部先例，未核实实现细节。）
- **任务书**：死亡经济、世界重置、掉落、存档、PvP 结算等机制有大量推导（§9–§25）。

### 3.2 反对面 / 未知（为什么现在不能判定）
| # | 未知 | 说明 |
|---|---|---|
| 1 | **bbport 本身** | 第三方 fork（Supermedo ← deadinside28），游戏 1.09 / CUSA03173，eboot 转 x86-64 后原生执行。稳定性、许可、维护、是否提供 Mod 加载或 Hook 接口，**全部未评估**（任务书陈述，未独立核实） |
| 2 | **Hook 与内存布局** | 任务书 §5.2 自己列出 7 项"必须确认"：内存管理、基址、函数地址分布、Hook 点、runtime 与游戏边界、Mod 加载时机、eboot 转换流程。当前完成 **0 项** |
| 3 | **网络与同步** | P2P / NAT / E2EE / 状态同步没有任何实测；`06 §4` 的"慢约一千倍"是量级估计，不是本项目数据 |
| 4 | **游戏机制可移植性** | §9–§25 的设计没有承接者，也没有和实际内存结构对过一次 |

### 3.3 判定与止损
- **判定**：未证明。不是"接近完成"，也不是"不可能"。
- **M0 可行性冲刺（时间盒 2~4 周，建议新增卡片）**：
  - `R-1` 环境与 bbport runtime 侦察 → `docs/re/bbport-runtime.md`（带证据等级）；
  - `R-2` 最小 Hook / 内存读写证明（读一个玩家状态、稳定存活、可复现）；
  - `R-3` 双进程 IPC 实测（共享内存往返延迟 + 事件丢失统计）→ 校准 `06 §4`；
  - `R-4` 双客户端最小同步（游戏侧先桩，验证网络/会话骨架）。
- **Kill criteria（示例，需 Human Owner 确认）**：`R-1` / `R-2` 在 2 周内给不出「进程内读写一个玩家状态且稳定存活」的可复现证据 → 立即重估：换运行时 / 收窄目标 / 停止。**不要在未证明的平台上继续铺 20 张卡。**

## 4. 模块化成败条件

### 4.1 值得肯定
单一职责、冻结接口、模块所有权、故障边界、门禁可查 —— 方向正确，也是这个仓库最扎实的部分。

### 4.2 风险（6 条）
| # | 风险 | 说明 |
|---|---|---|
| 1 | **边界来自推演，不是事实** | 附录 A 自己承认：v1 的 a2 拆成 `session_core`+`replication_core`、a3 拆成 5 个模块，跨层接口方向需要重定 —— 这说明模块图是**假设**，不是从 RE 里长出来的 |
| 2 | **冻结过早** | 7 个接口没有任何一次真实集成就被标成"冻结 v1"，改动要走 §52-c 流程；摩擦会把"改接口"逼成"绕过流程" |
| 3 | **进程边界提前** | `06` 要求两个可执行文件 + IPC + 生命周期 + 版本握手；收益真实，但代价在没有任何垂直切片时就要付（裁定保留，评估的是**顺序**） |
| 4 | **Layer Gate 没有对象** | Layer 0 出口条件依赖尚不存在的模块，当前无法执行，容易变成文档仪式 |
| 5 | **模块内部行为无人定义** | 任务书 §9–§25 的机制设计没有进模块；`docs/modules/` 只有 README |
| 6 | **命名 / 数量 / 归属歧义** | 注册表是「15 个 + 2 个贯穿性」= 17，但 T-007 / T-010 / 附录 A 的措辞不一致；`src/platform/README.md` 把归属指向 T-016（旧目录兼容），与 K-10 裁决不符 |

### 4.3 成功条件
1. **MVP 砍到 5~7 个模块**：Kernel + `game_hook` + `replication_core` + `transport` + `session_core` + `crypto` + `observability`；其余模块冻结。
2. **先垂直切片，后冻结接口**：v1 头文件降级为"草案（可修订）"，切片完成后冻结 v2；§52-c 的流程保留给 v2。
3. **每份模块任务书先写"原版行为约束"**（来自 §9–§25 并标行号），再写接口。
4. **每个模块必须有真实 owner、可运行测试、明确的失败行为**，否则不建。

## 5. 结构问题清单（10 条，带证据）

1. **需求覆盖断裂**：Phase 1（bbport 环境与 runtime 逆向）在附录 B 里没有承接卡 —— 整个项目风险最高的工作没有 owner。
2. **根 README 还是 v1**：仍在讲 13 个职能 Agent、`mod/` 路径；"当前状态"说 Phase 0 Not Started，与附录 B「Phase 0 已完成（docs/security 9 份）」矛盾。T-017 未做。
3. **数量与归属歧义**：15（+2 贯穿性）= 17；`src/platform/` 归属在 README 里指向 T-016，与 K-10 裁决冲突。
4. **接口冻结过早**：7 个头文件没有实现、没有集成，却被标为冻结 v1。
5. **模块行为缺位**：`docs/modules/` 只有一个 README；模块只定义了边界，没定义内部做什么。
6. **必需交付物缺失**：`REFACTOR-REPORT.md`（`AI_POLICY.md` §6 明确要求）不存在；`config/`、`tests/`、`scripts/` 基本都是占位 README。
7. **治理 / 产物失衡**：123 个 Markdown + 39 个 YAML + 25 个 Python（多数是门禁）对 1 个 `.cpp`；门禁主要在验文档与 CI 自身 —— 这和 `重构对照` 自己写的"有治理、无实现"是同一个问题，只是换成了 v2 的目录。
8. **单账号 + 单人 + 0 行内复查**：28 个已关 PR 全部由 AI-00 提交与合并；S0 方案已在推进，但平台审批必须等第二个账号。
9. **验证天花板**：本机无 MSVC / cmake；没有游戏侧测试；四级验证等级目前无内容可跑。
10. **任务书自身矛盾**：§3.6 原则 5 承诺「任一非核心模块崩溃，进程存活」，而 `06 §6` 已裁定进程内 11 个模块做不到 —— 任务书只增不改，**读者必须靠 `06` 覆盖它**。这类"源文件承诺与架构裁定冲突"的地方还会出现（只增不改的代价）。

## 6. 怎样做得更好（按优先级）

### P0（本周）
1. **加 M0 卡片 `R-1`~`R-4`**（见 §3.3），每条有产出、时间盒、kill criteria。**暂停新增门禁**：新门禁必须绑定一次真实缺陷或复盘，不得为"完备"而加。
2. **根 README 更新到 v2**（把 T-017 提前）：模块表、分支模型、真实状态；Phase 状态与附录 B 对齐。
3. **统一数量与归属表述**：写清「15 核心 + 2 贯穿性 = 17」；`src/platform/` 按 K-10 措辞（机制先收在 T-021 内的薄适配层）。

### P1（2~4 周）
4. **垂直切片先行**：2 个客户端 + 1 个区域 + 位置/HP 同步；可演示、有日志、可复现（游戏侧允许先桩，但必须至少打通 R-2）。
5. **接口解冻窗口**：v1 草案 → 切片后冻结 v2；在此期间允许小步修订，但必须在 PR 记录。
6. **MVP 模块裁剪**（见 §4.3-1）。
7. **把 §9–§25 映射到模块**：先出 `docs/modules/_template.md` + 2 份样板（`game_hook` / `replication_core`），证明"设计能落进模块"。

### P2
8. **M0 通过后再补框架**：T-005 / T-006 等按切片最小集实现；M0 不通过则按 kill criteria 处理，而不是继续补框架。
9. **复查与协作 S0 落地** + 第二账号准备（见 `docs/standards/协作与复查-改进方案.md`）。
10. **每 2 周一次"证据审计"**：只数三类东西 —— 可运行二进制、可复现的 RE 事实、可测的数字；文档与门禁单列，不再用"PR 数量 / 门禁数量"当进度。
