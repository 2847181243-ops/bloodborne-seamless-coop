# 可复用的工程结构与门禁（参考 build_in_harmonyos）

> **来源**：<https://gitcode.com/OpenHarmonyPCDeveloper/build_in_harmonyos>
> OpenHarmony 平台开源软件编译兼容性框架，Apache-2.0，v12.2x。
> 抓取日期：2026-10-09。**本文只记录从它学到什么、哪些能用到本项目，不复制它的代码或文案。**
>
> 它和本项目是**同一类**：AI Agent 大规模协作 + 编译适配 + PR 门禁。
> 但它规模成熟得多 —— 已收录 2500+ 款软件、52 条铁律（R1-R52）、
> 320+ 错误模式（E001-E320）、8 道验证门禁、7870 个 PR 的评审数据。

## 1. 可复用的结构

### 1.1 `skills` 内容的三层组织（最值得直接采用）

它的 skill 不是一个大文件，而是**按读者意图分层**：

| 文件 | 回答什么问题 | 何时读 |
|---|---|---|
| `KNOW_YOUR_WHY.md` | **为什么存在**、绝对不能忘什么 | 每次任务开始 |
| `SKILL.md` | **怎么做**（骨架 + 要点） | 每次任务前 |
| `references/*.md` | 逐条详解（如 52 条铁律） | 按需加载 |

`SKILL.md` 开头明确写了分工：

> 骨架 + 要点，详解按需从 references/ 加载。
> KNOW_YOUR_WHY.md 回答"为什么"，本文档回答"怎么做"。

**为什么这样分**：SKILL.md 会被**完整加载进上下文**。它越长，每次任务的固定开销越大。
把"为什么"和"详解"外置，是为了让骨架保持可加载、详解保持可检索。

**它还有一条我们没做的**：

> 每次编译任务前先读本文档。

即**把"读 skill"写成流程的第一步**，而不是指望 Agent 自己想起来。

### 1.2 约束分级（我们有 R 编号，但缺少后果分级）

它把约束按**违反后果**分成三级：

| 级别 | 含义 | 例 |
|---|---|---|
| 💀 **致命级 D** | 违反一次造成**不可逆损失** | D1 补丁完整性校验：漏掉补丁 = 永久丢失知识 |
| 🔴 **严重级 S** | 违反导致**产物不可用** | S2 系统同名库未静态编译 → 其他应用崩溃 |
| ⚙️ **普通级 R** | 违反 = bug，可修 | R13 脚本调用必须用完整路径 |

每条 R 都附**具体教训**，例如 R43：

> task 3681 对 `Qt5::3DCore` 的 component/cmake_file_name/includedirs 反复推演调参 3.5 小时无一次阶段性上报，直到预算耗尽。

**对照我们的现状**：`docs/security/constraints.md` 的 C-001…C-019 只有"违反后果：FAIL"一档，
没有区分"可修复的 FAIL"与"不可逆损失"。**这是我应当补的。**

### 1.3 知识分层 L1/L2/L3 + 写入时机

```
遇到问题 → "下一个完全不同的软件也会遇到吗？"
  ├─ 是 → L1 平台真理 / L2 类别模式 → 写入 knowledge/
  └─ 否 → L3 本版笔记 → 写入 manifest.yaml
```

配套两条硬规则：

- **边做边记，禁止批量补记**（D2）："探索阶段每步实时记录，禁止编译完成后才提取"
- **索引必须同步**（D3）："归档后 SUMMARY.md 自动重建，索引落后 = 重复劳动"

**对照我们的现状**：我们的知识散落在任务书、`docs/`、Issue、PR 描述、`.dsh/skills/`。
**没有"什么该写哪里"的判断标准**，也没有"索引必须同步"的机制。
结果就是同样的问题会被不同 Agent 反复讨论。

### 1.4 单一 CLI 入口

所有操作走一个入口：`scripts/ohc-run.py <子命令>`（build / init-build / conan-init /
conan-verify / finish / engine / graph / resolve-deps / status / handoff / submit / review）。

**为什么重要**：Agent 不需要记"这件事该跑哪个脚本"，
而且**流程本身可被工具化**（状态恢复、断点续跑、预算检查都挂在同一个入口上）。

我们目前是**多个独立脚本各自为政**：`preci.ps1`、`check_style.py`、
`validate_workflows.py`、`fetch_pr.py`，以及一堆只在 scratch 目录里的临时验证脚本。
**这是我该收敛的。**

### 1.5 AI 层与 CI 层严格分离（我们已做对，确认一下）

| 层 | 内容 | 特征 |
|---|---|---|
| AI 层 | `scripts/ohc-run.py` + `ci/scripts/preflight_check.sh` | 需要智能、可跳过、本地跑 |
| CI 层 | `ci/conan/*.sh`、`ci/artifacts/sign.sh` | **纯 shell + conan，不依赖 AI 工具、知识图谱、草稿机制** |

原文：

> CI 纯 zsh + conan，不依赖 ohc-run.py / 知识图谱 / 草稿机制
> Upload 安全边界：密钥仅存 CI 执行机，PR 校验不 upload

**对照我们的现状**：`tools/preci/`（AI/本地层）与 `.github/workflows/`（CI 层）已经分离，
但**预检复用 CI 的判据**（比它更进一步）。这一条我们已经做对。

## 2. 可复用的门禁设计

### 2.1 门禁分阶段 + 失败码（我们的门禁缺"失败码"）

| 阶段 | 时机 | 内容 |
|---|---|---|
| **L0** | `conan create` **之前** | 11 项静态检查（目录/文件/方法/清单/语法/URL/patch 格式/版本冲突） |
| **L1** | `conan create` **之后** | 5 项验证（测试痕迹、真测试检测、**破坏性反向验证**） |
| **L2/L4/L5** | 验证阶段 | 烟雾测试 / 安全扫描（NX/PIE/RELRO）/ 产物 SHA256 基线 |

每项检查都有**失败码**（`no_test_package_dir`、`stub_test_method`、`baseline_mismatch` …）。

**为什么失败码有用**：日志里能直接搜 `L0d`，而不是读一句自然语言描述再猜是哪条规则。

**我们的现状**：门禁报的是中文句子（如"章节「如何验证」是空的"），
**没有稳定标识符**。想引用某条门禁只能复制整句。**这是我该补的。**

### 2.2 「偷懒检测清单」——这张表最值钱

它把每种偷懒方式**显式对到**捕获它的门禁上：

| 偷懒方式 | 被哪层捕获 |
|---|---|
| 不写 test_package | L0a |
| 写空壳 `test()` | L0d |
| `test()` 假运行（`echo ok`） | L0d + L1d |
| **假测试源码（`int main` 只 printf）** | 代码审查 + L1b |
| 不跑 `make check` | L1c（日志无痕迹） |
| 提交 Go/Rust 项目（非 C/C++） | L0f |
| **`self.run()` 中裸用 `${CC}`** | L0h |
| **同版本号重复上传不同配方** | L0j |
| **test 不调用被测包 API** | **L1e 破坏性反向验证** |

**这张表的思路可以整体搬到我们这里**：不问"我们该加什么门禁"，
而问"**常见的绕过手段有哪些，每一种由谁捕获**"。

### 2.3 破坏性反向验证（最巧妙的一条，强烈建议采用）

**问题**：`test_package/test.c` 只 `printf("OK")`，即使被测库完全损坏也能通过。
它通过了 L0c（有源文件）、L0d（`test()` 调了 `self.run()`）、L1d（不是 `echo`/`print`/`true`）**所有检查**。

**解法（L1e）**：

```
1. 找到被测包产物
2. mv 移走整个产物子目录（bin/、lib/、include/）
3. 重新 conan test（重新编译 + 链接 + 运行）
4. 仍然 PASS → 假测试（不依赖被测包）
   失败     → 真测试
5. mv 目录回原位
```

**为什么无法绕过**（原文表格）：

| 包类型 | 破坏方式 | 底层保证 |
|---|---|---|
| 静态库 `.a` | mv `lib/` | 链接器必须找到库文件 |
| 动态库 `.so` | mv `lib/` | NEEDED 记录强制加载 |
| 可执行 `bin/` | mv `bin/` | 进程执行不可伪造 |
| 头文件库 | mv `include/` | 预处理必须解析声明 |

> 提交者无论在 CMakeLists.txt、源码、conanfile.py 哪一层做手脚，
> 都无法改变链接器/加载器/预处理器的确定行为。

**对照我们的现状**：我们的 `docs/audit/` 双人签核是**人写的报告**，
`security-gate` 只检查"报告存在 + 结论行格式 + 双人签名"——
**完全没有验证结论是否属实**。这正是 L1e 要解决的问题类型。

它还有一条 R52 专门防这个：

> 审计 pass 但硬闸命中 → 「**审计失真**」一票否决档（#2204/#4237/#4321：审计文件可伪造或自审走样）

### 2.4 前置预检（preflight）——与我们思路一致，但更细

它有独立的 `ci/scripts/preflight_check.sh`，本地跑，机械拦截：

| 闸 | 拦什么 |
|---|---|
| PF3 | `test()` 空壳（AST 检测）+ 无测试源文件 + MANIFEST 缺失 |
| PF5 | patch 新增行含 `__OHOS__` → fail-closed |
| PF6 | 依赖注入到共享 `/usr/local` → fail-closed |
| PF7 | 源码 URL 非官方源（**14 域镜像黑名单**）→ fail-closed |
| PF8 | `commands.json` 存在性/schema |

注意 "**fail-closed**" 这个取向：命中就拦，例外必须**显式跳过并留痕**：

> 例外场景需 PR 说明理由后 `--no-preflight` 显式跳过（**留痕可审计**）

**我们的现状**：`tools/preci/preci.ps1` 已有 10 项，但**没有"显式跳过 + 留痕"机制**。
`-Strict` 是对 SKIP 从严，不是对绕过留痕。

## 3. 可复用的协作与流程

### 3.1 双角色 + 明确的"不可碰"清单

| 操作 | 协作者 | 主编 |
|---|---|---|
| 编译软件 | ✅ | 不做 |
| 知识图谱草稿 | ✅ | 不做 |
| 创建 PR | ✅ | 不做 |
| **合并/拒绝 PR** | ❌ | ✅ |
| 修改 `SKILL.md` / `references/` / `templates/` / `scripts/` / `ci/` / `index.tsv` / `SUMMARY.md` | ❌ **禁止** | ✅ |

**协作者 Git 铁律**：

> - ❌ 不推 main，不走捷径：创建功能分支 → push → PR
> - ❌ 不碰基础设施：… 只读
> - ❌ 不碰他人归档目录
> - ✅ 新增知识用 `graph add --draft`

**对照我们的现状**：我们有 `branch-policy.yml` 的 SCOPE 表（比它更精细），
但**没有"知识必须先草稿"这一层**（R17）。我们的 Agent 可以直接改 `docs/`。

### 3.2 PR 单目标原则（W2，CI 硬拦截）

> 每个 PR **只允许提交一个软件**。多个软件 = 拆成多个 PR，CI 检测到多软件目录会直接拦截。

**为什么**：单软件 PR 可独立 review、独立回滚、独立定位。
**对照我们**：PR 模板已有"本 PR 只解决一件事"，但**只是勾选项，没有机器校验**。
我自己的 PR #12 就把"编译标准"和"修复 CI 逻辑"混在一起了。

### 3.3 上游测试三步法（R51，真人评审第一拒绝原因）

> 7,870 PR 全量评论审计：「硬性不通过」**495 次**，第一原因就是"上游测试实际运行 + 通过率如实回填"。

三步：

1. **清点**：`tests/` 目录数 + ctest/pytest 注册数，写入申报表
2. **运行**：可运行的必须实跑；不可运行的**逐项列具体技术原因**
   （原文：**"没环境"四个字不是技术原因，评审直接拒**）
3. **回填**：填实测 `N/N'`/通过率，**禁占位符**（"待 CI 验证"直接被拒）

还有一条防造假：

> **"上游确无测试"的声明必须附清点证据**（tests/ 目录截图或源码树路径），
> 防 pixman 式谎报（实有 42 个测试文件被谎报为 0）

**对照我们**：任务书 §39 有验证等级（Compile → Runtime → Multiplayer → Regression → Feature），
但我们**没有"清点 + 实跑 + 如实回填"的强制格式**，也没有"没环境不算理由"这条口径。

### 3.4 止损与预算（我们完全没有）

| 规则 | 内容 |
|---|---|
| **R41 外部依赖阻塞止损** | registry/git remote 连续 3 次不可达且超 30 分钟 → 立即止损 |
| **R43 调参螺旋止损** | 同一错误类别连续 5 次调参失败 → 停止，写报告退出 |
| **R48 预算感知收尾** | 长阶段前 `budget-check`：ok / near_limit（<40min 收尾）/ exhausted |

配套教训：

> 教训不是"不等 CI"，而是"**不裸等**"：先落草稿，再用工具轮询，红了修到绿。

**对照我们**：**完全没有止损机制**。我在本轮里为了一个 PowerShell 编码问题
反复尝试了十几次 —— 正是 R43 要防止的行为。

### 3.5 覆盖 60% 未知的 CI 诊断

> CI 侧分类约 60% 落"未知"，`diagnose` 对评论内嵌失败日志做本地二次归类
> （链接/编译/cmake/依赖/配方/补丁/权限/网络/文件缺失/测试空壳），输出证据行 + 修复要点
> **禁止对"未知"失败盲改重推**

**对照我们**：我一直靠"读 runner 日志 + grep error 行"手工做这件事。
**这个方法有效且反复验证过**（本轮靠它定位了 `issues: read` 权限、章节边界、验证等级三个 bug），
但它**只在 scratch 目录里**，没进仓库。**这是我该收敛的。**

## 4. 建议本项目采用的部分（按性价比排序）

### 🔴 高价值 · 低成本（建议立即做）

| # | 事项 | 理由 |
|---|---|---|
| 1 | **门禁加稳定失败码** | 现在只能引用整句中文；加 `PG-012` 之类的码后可被搜索、引用、进 PR 模板 |
| 2 | **约束加后果分级**（致命/严重/普通） | 我们 C-001…C-019 只有"FAIL"一档，无法区分"可修"与"不可逆" |
| 3 | **"偷懒检测清单"** | 不问"加什么门禁"，改问"绕过手段有哪些、由谁捕获"。**这张表能直接指导我们补门禁** |
| 4 | **止损规则** | 本轮已实际发生"同一问题反复尝试十几次"；设"连续 5 次同类失败即停" |
| 5 | **`preci` 加"显式跳过 + 留痕"** | 现在跳过只是 SKIP；应要求写原因，且该原因进 PR 供审计 |

### 🟡 中价值 · 中成本

| # | 事项 | 理由 |
|---|---|---|
| 6 | **知识分层 L1/L2/L3 + 写哪里** | 我们的知识散在 5 个地方（任务书/docs/Issue/PR/skills），没有判断标准 |
| 7 | **`bbcoop-*` skill 三层化** | WHY / 骨架 / references，控制每次任务的固定上下文开销 |
| 8 | **破坏性反向验证的思路用于审计门禁** | 我们的双人签核只验格式不验属实 —— 这是最大的门禁漏洞 |
| 9 | **PR 单目标改成机器校验** | 现在是勾选项，我自己的 PR #12 就违反了 |

### 🟢 低价值或必须改造

| # | 事项 | 原因 |
|---|---|---|
| 10 | 知识图谱 / 错误模式引擎 | 他们 2500 款软件才需要；我们代码都还没有，**过早** |
| 11 | Conan 配方体系 | 我们不发布软件包，**不适用** |
| 12 | 主编/协作者双角色 | 我们是同一人扮演多角色，**不适用**；但"知识先草稿"可以借用 |
| 13 | 积分赛 / 任务上报机制 | 他们的平台产物，**不适用** |

## 5. 必须改造后才能用的部分（不要照搬）

| 它们的做法 | 为什么不能照搬 |
|---|---|
| 依赖 GitCode / AtomCode 平台 API | 我们在 GitHub；且我们的环境有 MITM，直连受限 |
| `ci/` 用 zsh | 我们是 Windows + PowerShell + bash(Git Bash) |
| 依赖 `conan`、`readelf`、`tool_requires` | 这些在 Windows/MSVC 环境下不可用 |
| 52 条铁律的具体内容 | 是 OpenHarmony/Conan 领域知识，与 Bloodborne 无关 |
| `#ifdef __OHOS__` 之类的平台守卫 | 我们是 Windows 原生进程 hook，不适用 |
