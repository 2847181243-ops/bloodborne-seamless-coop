# 绕过手段与门禁对照表（哪些偷懒会被抓住，哪些抓不住）

> **这份文件的用法**：不要问"我们该再加什么门禁"。
> 改问 **"常见的绕过手段有哪些，每一种由谁捕获？"**
> 后者能直接指出缺口，前者只会让人凭感觉加规则。
>
> 参考来源：`build_in_harmonyos` 的"偷懒检测清单"与 L0/L1 门禁设计。
> 它在 7870 个 PR 的评论审计中发现：**「硬性不通过」495 次，第一原因是"声称跑了测试但没跑"**。

---

## ⚠️ 先读这一节：本表**必须**诚实

一张只列"我们能抓住"的表是没有用的 —— 它会让人以为缺口不存在。
所以下表**刻意包含"抓不住"的行**，并说明为什么。

**"抓不住"不等于"不用管"**，而是"这一项依赖人，机器帮不上"。
知道哪些依赖人，才知道该在哪里格外小心。

## 1. 代码层面

| 绕过手段 | 捕获者 | 现状 |
|---|---|---|
| 为了编译通过而**删掉功能** | 任务书 §38 + 人工 review | ⚠️ **抓不住**：机器无法判断"少了一个函数"是删功能还是重构 |
| 为了消除报错而**大面积注释代码** | `check_style.py` 的注释纪律（§38） | ✅ 已实现：新增行里注释占比超阈值就报 |
| **空实现桩**（`return 0;` 假装功能完成） | 任务书 §38 + 人工 review | ❌ **抓不住**：需要一个"该函数应有的行为"的规格才可能机器判定 |
| 源文件**缺文件头注释** | `check_style.py` | ✅ 已实现（负例矩阵已验证） |
| 提交**编译不过**的代码 | `build.yml`（MSVC 真编译）+ `/WX` | ✅ 已实现（有源文件后生效） |
| 提交**有警告**的代码 | 同上，`/WX` 把警告变错误 | ✅ 已实现 |
| GBK 乱码 / 非法 UTF-8 | `repo-integrity` + `preci` 编码检查 | ✅ 已实现 |
| 二进制文件混进提交 | `preci` 编码检查（按内容探测 NUL） | ✅ 已实现（本轮刚修：`.pyc` 曾漏过） |
| **凭据 / 私钥**入库 | `preci` 凭据扫描 + `security-gate` | ⚠️ **部分**：能抓明文与常见模式，**抓不住 base64 内嵌的凭据** |
| 抄来的代码不标来源 | — | ❌ **抓不住**：需要全互联网代码比对 |

### 其中最危险的一行

**`return 0;` 假装功能完成** —— 这是任务书 §38 明令禁止的第一条，
而我们的门禁**完全抓不住**。

**为什么抓不住**：要机器判断"这个函数没做事"，需要知道"它应该做什么"。
那等于要求有形式化的规格说明。

**所以这一项只能靠人。** 对策不是"加个门禁"，而是：

- 审计时必须**读实现**，不能只看"函数存在"
- 验证等级声明（§39）必须**逐级**：`Compile Verified` 不等于 `Runtime Verified`
- 不能因为"编译过了"就往上声明等级

## 2. 测试与验证层面

| 绕过手段 | 捕获者 | 现状 |
|---|---|---|
| 声称跑了测试但**没跑** | — | ❌ **抓不住**：我们还没有任何自动化测试 |
| 测试是**空壳**（只 `printf("OK")`） | — | ❌ **抓不住**：没有反向验证机制 |
| 测试**不调用被测代码** | — | ❌ **抓不住**：同上 |
| 用**日志输出**冒充网络同步 | 任务书 §38 | ⚠️ 人工 review |
| 用 **Mock 冒充真实功能** | 任务书 §38 | ⚠️ 人工 review |
| 用**假数据**冒充逆向结论 | 证据等级分级（Confirmed/Probable/…） | ⚠️ 人工，但**有格式可查** |
| 跳级声明验证等级 | `pr-guard` 的验证等级判定 | ✅ 已实现（本轮修好：不再把"不适用"当声明） |
| 把 CI 失败记成 pass | — | ❌ **抓不住**（我们还没有 CI 结果回填机制） |

### 这里有一个可以借用现成做法的缺口

`build_in_harmonyos` 用**破坏性反向验证**解决"空壳测试"：

```
1. 找到被测包的产物目录
2. mv 走整个 bin/ lib/ include/
3. 重跑测试
4. 仍然通过 → 假测试（不依赖被测物）
   失败     → 真测试
5. mv 回原位
```

它无法伪造，因为**链接器必须找到库文件**、**加载器必须加载 NEEDED 记录**、
**预处理器必须解析声明** —— 提交者在哪一层做手脚都改不了这些确定行为。

**我们能用的版本**（等有了源文件与测试之后）：

- 把 mod 的核心函数**移走或改名**，重新编译测试 → 测试若仍通过，说明它没测那个函数
- 把导出的符号**改掉**，看测试是否失败
- 这类验证必须**留在 CI 里**，不能只做一次

## 3. 流程与 PR 层面

| 绕过手段 | 捕获者 | 现状 |
|---|---|---|
| **直接推 main** | ruleset `main-protection`（deletion / non_fast_forward / linear history） | ✅ 已实现 |
| 绕过 PR 流程 | ruleset 要求 pull_request | ✅ 已实现 |
| PR **不填模板** | `pr-guard` 章节检查（7 个必需章节非空） | ✅ 已实现 |
| PR **关联不存在的 Issue** | `pr-guard` + `gh api` 核对 | ✅ 已实现（CI 里；本机无 gh 时如实报 notice） |
| PR **标题与内容中英夹杂 / 自造比喻** | — | ❌ **抓不住**：语言质量无法机器判定（已写进 CONTRIBUTING 3.0，靠人） |
| PR **混入多个不相关的改动** | — | ⚠️ **部分**：模板有勾选项，但**没有机器校验** |
| **越界修改别人的模块** | `branch-policy.yml` SCOPE 表 | ✅ 已实现（负例矩阵 8/8） |
| 从**过期基线**开分支（stacked PR） | `branch-policy` 的 ownership + 人工 | ⚠️ 部分：本轮我自己踩过（PR #4 叠在 #3 上） |
| 用 `--no-verify` 绕过本地钩子 | — | ⚠️ **设计如此**：本地钩子**本来就可绕过**，真正强制的是 ruleset + CI |
| 跳过本地预检直接提 PR | — | ⚠️ **抓不住**：这是流程约定，没有技术强制 |

### 关于最后一行（要诚实）

**"所有 PR 必须先本地预检通过"这条，目前是流程约定，不是技术强制。**

技术上无法阻止有人在没跑预检的情况下提 PR。
能做的是：把不跑预检的**后果**变得明显（CI 会红），以及**让它容易跑对**。

声称某件事"已被强制"而实际只是"约定"，是比没有门禁更糟的状态。

## 4. 知识层面

| 绕过手段 | 捕获者 | 现状 |
|---|---|---|
| 编译/调试完**不记录任何知识** | — | ❌ **抓不住**：经验随会话消散 |
| 记录**不完整**（漏掉关键补丁/步骤） | — | ❌ **抓不住** |
| 结论**没有证据等级** | 证据等级分级要求 | ⚠️ 人工，格式可查 |
| 把**推测**写成**已确认** | `docs/security/` 的三档标注（待裁决/待确认） | ⚠️ 人工，**但已有格式** |
| 重复记录 / 索引与内容不一致 | — | ❌ **抓不住** |

**这是本项目最大的持续风险**：我们做过的事如果没有记录，
下一个 Agent（或下一个会话的我）会从零开始 —— **这正是本轮反复踩同一个编码坑的原因**。

## 5. 总结：缺口按优先级

| 优先级 | 缺口 | 能否机器化 |
|---|---|---|
| 🔴 高 | `return 0;` 空实现桩 | ❌ 需要形式化规格，**只能靠人** |
| 🔴 高 | 空壳测试 / 测试不调用被测代码 | ✅ **可以**：破坏性反向验证 |
| 🔴 高 | 审计结论是否属实 | ✅ **可以**：让结论附带可核对的证据（哈希/命令输出） |
| 🟡 中 | PR 多目标混装 | ✅ **可以**：检查 diff 是否跨越多个模块 |
| 🟡 中 | 知识未记录 | ⚠️ 部分：可检查"归档目录是否有 notes 字段" |
| 🟢 低 | 凭据 base64 内嵌 | ✅ 可以（加解码后再扫） |
| 🟢 低 | 标题语言质量 | ❌ 只能靠人 |

**下一步该做的三个（都是"可以机器化"的高优先级项）**：

1. **破坏性反向验证**用于测试（等有测试之后）
2. **审计结论必须附可核对证据**（现在双人签核只验格式）
3. **PR 单目标机器校验**（检查 diff 是否跨模块）
