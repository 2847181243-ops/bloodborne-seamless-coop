# 需要 AI-C2 执行的任务：安全约束加「违反后果」分级

> **为什么这份文件在 `docs/standards/` 而不是直接改 `docs/security/constraints.md`**
>
> `docs/security/` 的所有权属于 **AI-C2**
> （`branch-policy.yml` 的 `[c2]="docs/security/"`，`CODEOWNERS` 指向 `/docs/security/`）。
> AI-00 直接改它会造成越界 —— 本地预检会拦下（我已在 `docs/audit/` 上踩过一次）。
>
> 所以这里只**记录要求并给出具体分级判定**，由 AI-C2 在自己的分支上落地。
> 分级判定我逐条写了，不是让 AI-C2 从头想 —— 那只是把工作推给别人。

## 1. 问题

`docs/security/constraints.md` 的 19 条约束，**五要素齐全**
（要求 / 理由 / 适用范围 / 验证方式 / 违反后果 —— 实测 19/19 都有），这一点做得很好。

但 `违反后果` **全部是同一个值 `FAIL`**。

**这丢失了一个关键区分**：违反 C-003（生成了持久标识）与违反 C-005（忘了包大小上限），
严重程度差得很远：

| | 违反 C-003 | 违反 C-005 |
|---|---|---|
| 能否"改回来" | **不能** —— 玩家隐私已经暴露 | 能 —— 加个上限就好 |
| 对玩家的伤害 | 不可逆 | 可修复 |
| 应该的处理 | 阻断 + 全量排查是否已发出 | 阻断 + 修好重审 |

**全是 FAIL 的实际后果**：审计者与实现者都无法判断该多小心，
于是倾向于"都一样扱重"或者"都一样可以商量"。分级就是为了消除这个模糊。

## 2. 建议的分级定义

借自 `build_in_harmonyos` 的三级约束体系
（见 `docs/standards/参考-build_in_harmonyos-可复用经验.md` 第 1.2 节），
但**按本项目改写**，不是照搬它的 D/S/R 措辞：

| 级别 | 标记 | 判据 | 处理 |
|---|---|---|---|
| **致命** | `致命` | 违反一次造成**不可逆损失**：隐私永久暴露、存档损坏、破坏反作弊公平、使玩家被平台封禁 | **一票否决 + 必须排查已造成的影响范围**，不允许"修好再合" |
| **严重** | `严重` | 产物不可用或产生**假阳性伤害玩家**：崩溃、无法连接、误判正常玩家 | **一票否决**，修好并重新审计后可合并 |
| **普通** | `普通` | 违反=缺陷，但**可修复且无持续伤害**：缺上限、缺日志、字段未按白名单 | 阻断合并，但属常规返工 |

**三级的共同点：都是阻断合并。** 分级改变的是**处理方式与紧迫度**，
不是"能不能放过"。这一条要写清楚，否则分级会被误读成"普通级可以不修"。

## 3. 逐条分级判定（19 条）

> 以下是 AI-00 的建议判定。**AI-C2 有权修改**，但改任何一条都要写明理由 ——
> 分级的价值在于"有人认真想过"，不在于谁定。

### 致命（4 条）—— 不可逆损失

| 编号 | 标题 | 为什么致命 |
|---|---|---|
| **C-003** | 无持久标识 | 一旦生成持久 ID 并出网，**隐私已经暴露，无法收回** |
| **C-004** | 无隐私数据出网 | 同上，IP / 账号 ID 一旦发出就收不回 |
| **C-016** | 日志中不得出现隐私数据 | 日志会落到磁盘、被分享、进 issue —— **扩散不可控** |
| **C-018** | 存档写入原子化与来源白名单 | **存档损坏不可逆**，玩家的游戏进度直接消失 |

### 严重（7 条）—— 产物不可用或假阳性伤害玩家

| 编号 | 标题 | 为什么是严重 |
|---|---|---|
| **C-001** | 端到端加密强制 | 明文路径使整个安全模型失效；但是"可发现并修" |
| **C-002** | 中继零信任 | 中继能解密等于 E2EE 失效；同上 |
| **C-009** | 消息完整性（HMAC + 序列号） | 无完整性校验 → 篡改与状态错乱 |
| **C-010** | 防重放 | 重放 → 物品复制，**破坏游戏经济**；但可加检测回滚 |
| **C-012** | 反作弊仅限 PvP | 在 PvE 误判会**伤害正常玩家**，违背本项目定位 |
| **C-013** | 客户机自我保护 | Host 作弊时客机无保护 → 玩家被单方面伤害 |
| **C-019** | 非法物品四类检测 | 非法物品进入世界污染存档；但可检测可清理 |

### 普通（8 条）—— 可修复、无持续伤害

| 编号 | 标题 | 为什么是普通 |
|---|---|---|
| **C-005** | 速率限制与包大小上限 | 缺上限是缺陷，补上即可，无持续伤害 |
| **C-006** | 抗 Sybil | 信誉体系没做好可调，不是不可逆的 |
| **C-007** | 失败不静默 | 缺日志影响可观测性，修了就好 |
| **C-008** | 版本强校验 | 版本不匹配拒绝连接 —— 行为保守，缺陷只是漏判 |
| **C-011** | 中继仅转发（可见性最小化） | 与 C-002 同源；此项关注"能看到什么"的收窄 |
| **C-015** | 会话密钥轮换与私钥不落盘 | 私钥落盘是严重问题，但"不轮换"本身可补 |
| **C-017** | 本地黑名单字段白名单 | 多存一个字段可删，无不可逆后果 |
| **C-014** | 【条件条款】公钥指纹验证 | **条件条款，未裁决前不约束实现方** —— 分级待裁决后定，暂列普通 |

> ⚠️ **C-015 需要 AI-C2 复核**：它的要求里同时包含
> "会话密钥定期轮换"（可补）与"私钥不落盘"（一旦落盘可能已被窃取）。
> 如果拆成两条，后者应升为**致命**。我在建议里没有擅自拆分，
> 因为拆分改变编号体系，应由 AI-C2 决定。

## 4. 落地要求

### 4.1 每条约束的后果字段改成

```markdown
- **违反后果**：致命 —— <一句话说清不可逆在哪>
- **违反后果**：严重 —— <一句话说清产物如何不可用 / 如何伤害玩家>
- **违反后果**：普通 —— <一句话说清这是常规返工>
```

**只写级别不写理由是不够的。** 级别是分类，理由才是判据。

### 4.2 在文件开头补一节

说明三级定义与"三级都阻断合并"这一点（第 2 节的内容可直接用）。

### 4.3 更新 `docs/audit/README.md` 的检查项表

审计报告模板里 `A-001…A-010` 的检查项应能对应到约束级别，
让审计者知道每项违反了属于哪一级。这属于 **AI-C3** 的范围
（见 `docs/standards/handoff-审计证据模板.md`）。

## 5. 机器校验（AI-00 会加，AI-C2 要让它过）

门禁会检查 `docs/security/constraints.md`：

1. 每条 `### C-XXX` 都必须有 `违反后果` 字段；
2. 后果字段必须**以三级之一开头**（`致命` / `严重` / `普通`）；
3. 后果字段除级别外必须有**理由**（不能只有级别两个字）；
4. 文件里必须有三级定义的说明节。

**这个校验会在 AI-C2 改完之前一直红。** 这是刻意的：
它把"欠的分级"变成可见的、有具体位置的待办，而不是一句"以后再说"。

如果 AI-C2 认为不应加这个门禁，请在 PR 里说明理由 ——
门禁本身也可以被讨论，但要有记录。
