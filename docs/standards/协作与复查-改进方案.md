# 协作与复查改进方案（S0 ~ S4 分阶段）

> **来源**：Issue #40；先例见 [`docs/references/REF-004`](../references/prior-art-code-review.md)（代码复查机制）、
> [`REF-005`](../references/prior-art-collaboration.md)（多人协作与贡献者治理）、
> [`REF-006`](../references/prior-art-harmonyos-review-collab.md)（build_in_harmonyos 评审与协作增量）。
>
> **性质**：提案 + 执行表。**涉及平台设置（ruleset / Organization）与 `MAINTAINERS.md` / `AI_POLICY.md`
> 的改动需要 Human Owner 批准**；其余 S0 项在本方案合入后拆成小 PR 落地。
>
> **最后更新**：2026-10

## 1. 现状与证据

| 事实 | 数据 / 来源 |
|---|---|
| 全仓库历史的 PR 行内复查评论 | **0 条**（GitHub API `GET /repos/.../pulls/comments`） |
| 已关闭 PR | 28 个（26 合、2 关）；全部由 AI-00 自己提交与合并 |
| `main` 规则集 | `approvals=0`、`require_code_owner_review=false`、`required_review_thread_resolution=true`、`dismiss_stale_reviews=true` |
| `develop` 规则集 | `approvals=0`、`code_owners=false`、`thread_resolved=false`、`dismiss_stale=false`（与 main 不一致） |
| 现有替代机制 | 6 项必需检查、preci 两阶段、PR 模板 8 节 + 决策记录、安全审计文本双签、branch-policy 所有权、squash + 线性历史 |
| 平台硬约束 | **PR 作者不能批准自己的 PR**（`github/docs`）；单账号下 `approvals>=1` 会永久阻塞（`MAINTAINERS.md` §4.1 已记录） |

**结论**：机器护栏不弱（门禁、预检、模板、审计都在），**缺的是「有人真的看懂」这一层**；
多人协作的机制（角色、指派、审批、合并自动化）基本没建。
两者都不该靠更严的口号，而应落到「机器能查的归机器、需要人的留下事实」。

## 2. 原则

1. 复查的目标是**有人看懂并敢负责**，不是多一个勾。
2. 机器能查的绝不靠勾选；不能机器查的，必须留下**谁、对哪个版本、看了什么、发现什么**的事实记录。
3. 不制造假闸门：单账号阶段不启用必需审批（会锁死），也不拿 AI / 机器人冒充人类复查。
4. 按规模触发：每个新机制写明触发条件，不提前上、也不裸等。
5. 先例可用但要改造：借 k8s / Chromium / Rust / systemd 的**判据**，不照搬它们的规模装置。

## 3. 分阶段方案

### S0 —— 现在（1 个账号）：机器能查的先拉满 + 独立复查留痕

| # | 事项 | 机器可查？ | 代价 | 先例 | 备注 |
|---|---|---|---|---|---|
| S0-1 | **评审清单版本化**：`docs/standards/review-memory.md`（短、按类别、每条挂本项目先例：C-xxx / 门禁码 / PR 编号）；复查时整篇注入复查上下文 | 文件存在、非空、引用格式 | 低 | REF-006 F1 | 直接可用 |
| S0-2 | **独立复查步骤**：每个 PR 由**非作者上下文**（另一个会话 / 队友）复查，结论与发现写进 PR 评论；PR 模板新增「复查记录」节（复查者、被查 sha、查了什么、发现与处置、遗留风险） | preci 阶段 2 校验该节非空且含 sha 与结论 | 中（每 PR 一轮） | REF-004 A7/A10、C1 | 单账号下唯一能做的「第二双眼睛」，必须标注为 AI 复查 |
| S0-3 | **复查意见闭环**：每条意见必须回复；`accept` 才可标记 resolved；`reject` 必须在讨论串写理由且**不自标** resolved | 评论状态可统计 | 低 | REF-006 F5 | 防「看过=处理过」 |
| S0-4 | **审计报告升级**：每条结论标 `rule_ref`；`pass` 附被检文件 sha256；preci 增加「审计 pass 与硬闸命中矛盾 = 审计失真」fail-closed | 机器可查 | 中 | REF-006 F3/F4 | 补「双签只验格式」的洞 |
| S0-5 | **占位符与产物路径**：PR 描述残留 `(请填写)` / `#___` → fail；Agent 的产物写到哪里用一张唯一权威表固定 | 机器可查 | 低 | REF-006 F7/F9 | 防路径试探与占位符 |
| S0-6 | **编号单源**：新增门禁码 / 约束编号必须登记到唯一权威文件，并加「文档 ↔ 实现」一致性测试 | 机器可查 | 低 | REF-006 F13 | 华为仓库已踩过编号漂移 |
| S0-7 | **PR 大小预警**：>300 行（排除 tests）自动警告；跨多个所有权目录必须拆 | diff stat 可查 | 低 | REF-004 A3、REF-005 E1 | 警告不阻断 |
| S0-8 | **AI 披露**：PR 模板必填「AI 参与方式 + 人工理解与验证」；标题 / 标签标注 AI 辅助；DCO 若启用只允许人类签（AI 用 `Assisted-by`） | 模板字段 + diff 检查 | 低 | REF-004 D1/D2/D3 | 我们是 AI 作者，这条是自证责任 |
| S0-9 | **OWNERS / CODEOWNERS 骨架**：按模块写 reviewer / approver（先写文件，不启用强制审批）；同期写下不活跃与 emeritus 规则 | 文件存在且与 `MAINTAINERS.md` §4 一致 | 低 | REF-005 A4/A5/A6 | 等第二人一到即可启用 |
| S0-10 | **迁到 GitHub Organization**（须批准）：merge queue、bypass 白名单、团队 auto-assign 的前置 | `owner.type` | 低-中 | REF-005 A2/D3 | 见 §4 |

### S1 —— 第二个人确定后

- [ ] 第二人权限只给 Write（不给 Admin / Maintain）。
- [ ] `main` 与 `develop` **同时**开启：`approvals=1` + `Require review from Code Owners` +
      `Dismiss stale approvals` + `Do not allow bypassing`；两套阈值一致（不能一严一松）。
- [ ] 作者不得合并自己的 PR；合并由非作者或 Human Owner 执行。
- [ ] `CONTRIBUTING.md` 拆出「人类贡献者」一节（与 AI 协作规约并列）。

### S2 —— 2 ~ 3 人

- [ ] 自动指派（CODEOWNERS / 轮换算法）+ 每人容量上限 + Busy / 休假开关。
- [ ] 每周固定 triage 时间；`good first issue` / `help wanted` 按「任务清晰、有背景阅读、有相似实现」的标准写。
- [ ] 角色三级（贡献者 → Reviewer → Approver / Owner）与晋级标准（客观计数 + 现任提名 + 公示无异议）。

### S3 —— 3 ~ 5 人

- [ ] 第二个 Approver 出现后，大改动要求 2 人批准。
- [ ] office hours / shadow：新人跟一次评审、跟一次发布。
- [ ] 开启 auto-merge（前置：分支保护已启用）。

### S4 —— 多贡献者、合并开始排队

- [ ] merge queue（前置：Organization + CI 支持 `merge_group` + 必需检查稳定）。
- [ ] 季度复盘（只记事实）：PR 大小、首次复查响应、复查意见数、批准人分布、复查后变更次数、逃逸缺陷。

## 4. 需要 Human Owner 批准的单项

1. **迁 GitHub Organization**（S0-10）——影响仓库地址与权限模型，且是 merge queue 的前置。
2. **DCO 或 CLA 二选一**——同人 Mod 涉及第三方 IP，法律适用性需你判断。
3. **修改 `MAINTAINERS.md` / `AI_POLICY.md`**——若要把「独立复查」写成硬规则；按规矩 AI 不能自改。
4. **S1 的平台审批开关**——需要第二个账号到位后再开，开之前确认不会把自己锁死。

## 5. 明确不采用 / 暂缓

| 做法 | 原因 |
|---|---|
| Chromium「每个目录 owner + 两名 committer」硬门槛 | 单人仓库无法满足；2 人后先引入「至少 1 名非作者批准」 |
| k8s Tide / Rust bors / triagebot 全量复制 | 规模不匹配；只借「双标签、自动指派、容量、休假」判据 |
| Copilot 自动批准 | 官方文档明确其默认**不计入**必需审批；只能作非阻塞建议 |
| 用机器人 / AI 冒充人类复查 | 禁止；AI 复查必须标注，且默认只作建议，除非 Owner 明确背书 |
| 「复查质量分数」 | 没有一手项目这么做；只记录事实（谁、何时、对哪个版本、几条意见、是否失效） |

## 6. 度量（只记事实，不做分数）

| 指标 | 取法 | 用途 |
|---|---|---|
| PR 大小（行 / 文件数） | `GET /pulls/{n}` | 观察是否出现巨石 PR |
| 首次复查响应时间 | PR 创建 → 第一条复查评论 | 观察是否「没人看」 |
| 复查意见数与闭环率 | 评论 + resolved 状态 | 观察是否走过场 |
| 批准人分布 | reviews 列表 | 观察是否集中在一个人 |
| 复查后变更次数（dismiss 计数） | ruleset + reviews | 观察「先批后改」 |
| 逃逸缺陷 | 合并后新建的 defect Issue | 唯一的滞后质量信号 |

## 7. 落地顺序

1. 本方案合入（Issue #40）。
2. S0-1 / S0-2 / S0-3 / S0-5 / S0-7 / S0-8 拆成 1 ~ 2 个小 PR（`lead/*`）先落地。
3. S0-4 / S0-6 / S0-9 随审计与门禁改动跟进（每个 PR 只解决一件事）。
4. S0-10 与 S1 的开关，等 Human Owner 决定与第二个账号到位。

## 8. 与现有文件的关系

- 本方案**不改**任何现有规则文件；S0 项落地时按「一个 PR 只解决一件事」拆开。
- 「独立复查」若成为硬性要求，属于**收紧**门禁（不是放宽），按现行授权可由 AI-00 走 PR 实施并在 PR 中说明；
  平台级审批（S1）必须等第二个账号，任何绕过平台自批的做法都被本方案禁止。
