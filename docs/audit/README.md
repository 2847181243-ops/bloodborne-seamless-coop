## 1. 审计阶段

```text
设计审计（实现前）  → 审计 docs/security/ 的架构与约束
代码审计（合并前）  → 审计所有网络相关代码
密码学审计          → 验证加密实现正确（AI-C1 的代码）
隐私审计            → 验证无隐私泄露
持续审计            → 每次网络代码变更都触发
```

## 2. 审计结论

```text
PASS                 通过
PASS_WITH_WARNING    通过，但有需要跟踪的警告（必须建 Issue）
FAIL                 一票否决，阻断合并
```

`FAIL` 不可被 AI-00 或开发方推翻。若开发方认为审计结论有误，走 `docs/conflict_log/` 裁决流程，
但**在裁决完成前保持阻断**。

## 3. 可核对证据（必填，缺一即阻断合并）

> **为什么要有这一节**：此前门禁只验格式 —— 报告存在、结论行合法、双人签名。
> **结论是否属实完全没有验证。** 编一段话加两个签名就能通过。
> 那等于门禁只防笔误，不防造假。
>
> 现在每条证据必须给出**被检文件的路径**与**该文件的 sha256**，
> 门禁会**重算并比对**；哈希不符、文件不存在、或文件不在本 PR 改动范围内，一律阻断。

**格式**（每行一条，`|` 分隔）：

```text
- 证据：<仓库内相对路径> | sha256=<64 位小写十六进制> | <查了什么>
```

**范例**：

```text
- 证据：mod/security/crypto.cpp | sha256=3b1f...（64 位）| 逐行核对 HMAC 覆盖范围，A-001 通过
- 证据：mod/network/session.cpp | sha256=a90c...（64 位）| 核对序列号单调性与重放窗口，A-002/A-003 通过
```

**算哈希**：

```bash
sha256sum mod/security/crypto.cpp          # Linux / Git Bash
certutil -hashfile mod\security\crypto.cpp SHA256   # Windows
```

**规则**：

1. **至少一条**证据行，且必须通过核对。
2. 路径必须是**仓库内真实存在**的文件。
3. 该文件必须**在本 PR 的改动范围内** —— 防止拿一个无关的稳定文件凑数。
4. 哈希必须与文件**当前内容**一致 —— 若报告写完后文件又被改动，会被拦下（这是有意的：
   报告必须对应它审计的那个版本）。

**它能防住什么、防不住什么（要诚实）**：

| | |
|---|---|
| ✅ 防住 | 随手编一段"已复核"的结论。写哈希必须真的算过哈希，而算哈希的前提是文件在手边被检查过。 |
| ✅ 防住 | 审计后再改文件（哈希失配）。 |
| ✅ 防住 | 拿无关文件凑数（必须在改动范围内）。 |
| ❌ 防不住 | **抄哈希**：看一眼文件、不算内容、直接把哈希复制过来。 |
| ❌ 防不住 | 两个人实际上没有独立判断（这条只能靠流程纪律）。 |

**所以这不是"证明"，而是把零成本伪造变成必须接触真实文件。**
不要对外表述为"审计结论已被机器验证为真"。

## 4. 双人独立签核（必填，缺一即阻断合并）

> 两名审计者**各自独立**出具判定，不得相互代签。任一方 `FAIL` 即一票否决。
> CI（`pr-guard.yml` 的 `security-gate`）会校验本区：两个角色都必须出现，各自「判定」
> 必须与 PR 标签结论一致。
>
> ⚠️ **本机制是文本层强制**（CI 读取报告文本），**不是** GitHub 平台级双人审批。
> 仓库为个人账号且 CODEOWNERS 单账号，平台无法强制两名审批人。
> 因此「两名审计者是否真的独立」最终仍依赖流程纪律，不得对外表述为平台级保证。

- C3-a（密码学 / 协议 / 完整性）：范围 = E2EE、HMAC、序列号与时间戳防重放、密钥轮换、版本握手强校验
  结论：PASS
  依据：<检查项编号 / 文件:行号>
  审计者：<签署人标识>

- C3-b（隐私 / 中继 / 抗滥用）：范围 = 隐私红线、中继零信任、速率限制与包大小、抗 Sybil、反作弊范围（仅 PvP）
  结论：PASS
  依据：<检查项编号 / 文件:行号>
  审计者：<签署人标识>

> **格式要求（CI 会校验）**：每个角色条目后必须紧跟一行 `结论：<值>`，
> 取值只能是 `PASS` 或 `PASS_WITH_WARNING`，且必须与 PR 标签推导出的结论一致
> （`audit:passed`→`PASS`，`audit:warning`→`PASS_WITH_WARNING`）。
> 任一方写 `FAIL` 或取值不一致 ⇒ 阻断合并。
> 请勿把判定写进表格单元格 —— 单元格形式依赖列位置，解析易错。

## 4. 强制审计触发条件

只要 PR 触及以下任一内容，**必须**有对应审计报告才能合并：

- `mod/security/**`、`mod/network/**`、`relay/**`
- 协议定义 / 序列化 / 加解密 / 密钥管理
- 中继节点行为
- 反作弊与黑名单
- 存档写入路径（原子性、非法物品检测）
- 物品发放与奖励（防重复）

CI 门禁见 [`.github/workflows/pr-guard.yml`](../../.github/workflows/pr-guard.yml)。
