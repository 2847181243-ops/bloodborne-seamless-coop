# 抗 DDoS 机制（Anti-DDoS）

**所有者：AI-C2（Security Architect）｜产出：Phase 0｜实现方：AI-B1（传输）、AI-B2（发现）、AI-B4（中继）**
**证据等级：`Confirmed`（机制项逐条回溯任务书；具体阈值均为待确认）**

> **唯一需求来源**：`bloodborne.markdown`（任务书 v3.0）。冲突时以任务书为准。
> 约束编号见 [constraints.md](constraints.md)（本文件实现 `C-005`）。

---

## 1. 威胁与目标

- **威胁**：主动攻击——DoS / DDoS（§45.1 `:1736`）→ 资产 A-07。
- **攻击面**：信令层（连接建立前的资源消耗）与中继层（转发带宽与状态表）。
  两者都是"攻击者无需先通过身份验证即可触及"的入口，因此**必须各自独立设限**。
- **防御目标**：使攻击者**用少量资源无法显著削弱服务**，
  且**不引入隐私采集**（`C-004`）。

> ⚠️ **红线**：抗 DDoS **不得**以"记录并封禁来源 IP"实现最终态——
> 记录 IP 直接违反 `C-004`（无隐私数据出网）。**速率限制必须无状态或按临时会话标识**。

## 3. 强制项（进入 `constraints.md` `C-005`，可审计）

| 编号 | 要求 | 适用层 | 可验证性 |
|---|---|---|---|
| D-1 | 信令层**必须**有速率限制 | AI-B1 / B2 | 代码审计：每条接收入口存在限流检查 |
| D-2 | 中继层**必须**有速率限制 | AI-B4 | 同上 |
| D-3 | **必须**有**包大小上限** | AI-B1 / B2 / B4 | 代码审计：存在长度上限且**在分配内存前**检查 |
| D-4 | **新消息类型必须同样被覆盖** | 全部 | 审计项：对照消息类型清单逐项确认 |
| D-5 | 中继隐藏（不暴露节点拓扑与真实地址） | AI-B4 | 见 §4 |

**审计要点（`D-3` 容易被做错）**：包大小上限必须在**分配/拷贝之前**检查。
"先分配再校验"仍可被超大包触发内存压力，应判 `FAIL`。

## 4. 中继隐藏（Relay Hiding）

任务书只给出"中继隐藏"这一短语（§45.2 `:1768`）。以下为其**可验证拆解**：

| 编号 | 要求 | 依据与说明 |
|---|---|---|
| H-1 | 中继**不得**向对端披露其他中继的真实地址 | 与 `C-011`（中继仅能看到临时标识）一致 |
| H-2 | 中继之间/客户端与中继之间**只交换临时标识**，不交换持久地址 | `C-003` |
| H-3 | 中继**不得**参与拓扑广播 | 否则一次入侵即可获知全网结构 |
| H-4 | 节点发现不得以"已知中继列表"形式长期持久化 | `C-003`（无持久标识） |

> ⚠️ **如实标注**：任务书**没有**给出"中继隐藏"的实现方式（未提 onion routing、
> 未提跳数、未提引入层）。上表是**从 `C-003`/`C-011` 推导的必要条件**，
> 不是任务书明文。**本文件不发明具体机制**：实现方案须由 AI-B4 提出并交
> AI-C3 设计审计（`docs/audit/` 的设计审计阶段）。

## 5. 与性能预算的关系（§36）

§36（`bloodborne.markdown:1202-1220`）给出性能与网络指标：
`Ping / RTT / Packet Loss / Tick Rate / Replication Frequency / State Correction / CPU / Memory / Hook Overhead`。

- **速率限制不得以牺牲玩法为代价**：限流阈值必须与上述指标共同评估。
- ⚠️ **但 §36 未给抗 DDoS 的量化指标** → 见 §6。
- **冲突处理原则**：性能 vs 安全冲突时 → **AI-C2 裁决，安全优先**（§49 `:2031-2036`）。
  即：**不得**以"影响性能"为由放宽 `D-1…D-5`。

## 6. 待裁决与待确认（**AI-C2 不擅自裁决**）

### 待裁决-2：验收无判据

| 出处 | 情况 |
|---|---|
| §53 `bloodborne.markdown:2435` | AI-C4 验收含硬性 checkbox「DDoS 防御验证」 |
| §36 `:1108-1114` | 性能与网络指标中**没有任何** DDoS 量化基线 |

**冲突**：**「必须验收」但无判据** → 无法客观判定通过与否。

- **裁决方**：**AI-C2 + AI-C4**。
- **建议议题**（供裁决参考，**非本文件决定**）：
  1. 验收以什么量表达？（如"给定洪泛速率下，正常玩家的 RTT/丢包劣化上限"）
  2. 限流阈值如何与 §36 的 Ping/RTT/丢包预算共同取值。
  3. 是否需要区分"信令层被打满"与"中继层被打满"两个独立验收场景。

### 待确认项

| 编号 | 内容 | 确认方 |
|---|---|---|
| 待确认-2 | 速率限制与包大小上限的**具体阈值**（任务书未给） | AI-C2 / AI-B1 / AI-B4 |
| Q-04 | 中继节点数量上限与筛选门槛（影响 DDoS 承受面） | AI-B4 / AI-C2 |
| 待确认-3 | 时间戳窗口与 **500ms 延迟阈值**的兼容性——窗口过小会误杀正常延迟包，等同自我 DoS | AI-C2 / AI-B1 |

> ⚠️ **待确认-3 与本文直接相关**：时间戳窗口若小于实际网络抖动，
> 会造成**正常玩家被持续拒绝**——这本身就是一种"被动的可用性破坏"。
> 因此 `C-010` 的时间戳窗口取值**必须**与 §29.4 的 500ms 延迟要求联合确认。

**规则**：上述项在裁决前**不得**作为强制约束交付实现方，**也不得**被判 `FAIL`。

## 7. 反 DDoS 的**禁止**做法（合规红线）

以下做法在技术上"有效"，但**违反本项目约束，一律禁止**：

| 禁止做法 | 违反 |
|---|---|
| 记录来源 IP 用于后续封禁 | `C-004`（无隐私数据出网）、SECURITY.md §2 |
| 采集设备指纹/硬件信息做限流键 | `C-003`、`C-004` |
| 中心化封禁（共享黑名单、上报攻击者） | §2.4 非目标；无服务器架构 |
| 上传行为数据用于流量分析 | SECURITY.md §6 |
| 扫描进程 / 读内存判断"是否攻击者" | §2.4、SECURITY.md §2 |
| 在 PvE 模式下因"疑似攻击"自动踢人 | `C-012` |

> **允许的限流维度**：临时会话标识、消息速率、包大小、连接数。
> 这些均为**会话内/瞬时**数据，不构成持久标识。
