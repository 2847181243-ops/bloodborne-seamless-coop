# 降级矩阵

这份文档回答一个问题：**每个模块失败时，哪些功能降级、用户看到什么、进程是否还活着。**

矩阵覆盖 18 行：Kernel 1 行 + 15 个模块 + 2 个贯穿性辅助模块
（任务书 §3.6 注册表）。模块 ID 逐字沿用任务书 §3.6，未作改名。

---

## 1. 怎么读这张表

- **「降级的功能」写的是失效后不可用的能力**，不是模块内部实现细节。
- **「用户看到什么」是玩家能观察到的现象**，写成玩家能看见的话，便于测试时对照。
- **「进程是否存活」一列全部为「是」**，依据是任务书 §3.6 原则 5：
  任一非核心模块崩溃，进程存活，其他模块继续工作。
  ⚠️ 前提是「核心模块」清单已定义，而任务书没有给出该清单
  → 见 [00-overview.md](00-overview.md) O-1 与 [03-fault-isolation.md](03-fault-isolation.md) I-2。
  Kernel 一行是例外，它的失败行为由任务书 §3.6 注册表单独规定。
- 标「待定」的单元格表示任务书没有确定该行为。
  这些位置**不得**由实现方自行选一个做法，要按 `AI_POLICY.md` §3 建 Issue 问人。

矩阵只描述**失败之后的表现**；失败如何被检测、何时熔断，写在
[03-fault-isolation.md](03-fault-isolation.md)。

## 3. 不适用「降级继续」的情形

有三类情形不能按第 2 节的方式处理：

1. **加密不可用** → 拒绝联机，不提供明文通道
   （任务书 §3.6 原则 6、§3.7 全局 Gate 8；`MAINTAINERS.md` §3 第 1 条；
   `docs/security/constraints.md` C-001）。
2. **行为反作弊不可用** → 仅禁用 PvP，不放开 PvE 的检测限制
   （任务书 §3.6 原则 6；`docs/security/constraints.md` C-012）。
3. **版本校验失败** → 拒绝连接或拒绝加载，不尝试「先连上再说」
   （任务书 §32.1、§5.5；`docs/security/constraints.md` C-008）。

另外，`docs/security/constraints.md` §2 列出的「始终启用」项目
（版本握手、协议版本与 Session ID 校验、防重放与包大小、速率基础限制、
物品发放记账与唯一物品防重复、客机世界状态不写入个人存档、存档写入原子性）
不得因为任何模块降级而被放开。**降级只减少功能，不减少安全约束。**

## 4. 需要裁决的降级许可

下面四条是矩阵里真实存在的空缺：任务书规定了这些能力必须存在，
也规定了模块失败时进程要存活，但**没有写模块失败时这些能力允不允许消失**。
按安全优先原则，这些不能由实现方自行决定（任务书 §49；
`MAINTAINERS.md` §7「安全 vs 开发 → 安全审计，安全优先」）。

| 编号 | 问题 | 相关约束 | 裁决方 |
|---|---|---|---|
| D-1 | `mod.loot` 失败后，「唯一物品防重复」失效时是否允许继续联机 | 该能力属**始终启用**的联机基础完整性（任务书 §46.0、`docs/security/constraints.md` §2） | AI-C3（安全优先） |
| D-2 | `mod.save` 失败后是否允许继续联机 | `docs/security/constraints.md` C-018 要求存档写入原子化与来源白名单，违反后果为 FAIL | AI-C3（安全优先） |
| D-3 | `mod.observability` 失败后，C-007 要求的 `[SECURITY]` 日志如何满足 | `docs/security/constraints.md` C-007 是强制条款，适用于全部组件 | AI-C3（安全优先） |
| D-4 | `mod.security_audit` 失败后，合并是否被阻断 | 任务书 §37 规定「安全审计未通过」必须建 Issue；`docs/interfaces/c3_to_all_audit.md` 的 `FAIL` 是一票否决 | AI-C3 |

在裁决之前，实现方按「安全约束不因模块降级而放开」处理第 3 节的通用规则，
并预留接口位（`docs/security/constraints.md` §3 的规则同样适用于此）。

## 5. 与接口契约的冲突之处

`docs/interfaces/b3_to_b4_reputation.md` 描述的是 AI-B3（信誉层）到 AI-B4（中继）的接口，
但任务书附录 A 写明信誉**不再是独立层**，已并入 `mod.session_core` / `mod.discovery`，
而 §3.6 的模块注册表里没有信誉模块。因此：

- 该契约的 `selectRelay` / `isEligible` 等能力，在 v2.0 的模块划分下**没有明确的归属模块**
  → **待定：信誉逻辑放在 `mod.session_core` 还是 `mod.discovery`**，
  按 §52-c 的接口冻结流程重新确定方向（任务书 附录 A、§52-c）。
- 该契约为中继选择写了 fail-closed 规则：
  「全部候选不合格 → 返回空列表并明确报错，**不得降级到无信誉校验的节点**」。
  这条与本文第 2 节 `mod.relay` 一行的关系是：
  **中继模块失败时连接失败是允许的降级；但中继模块正常时，不得为了连上而跳过信誉校验。**
  两者不冲突，但必须在实现中分别验证。

## 6. 更新义务

出现下列任一情况时，必须同步更新本矩阵与故障注入套件（任务书 §52-d）：

- 新增一个模块；
- 一个模块新增对外的依赖；
- 一个模块的失败行为发生变化（原来会崩，现在降级；或反之）；
- 新增一类失败场景。

本矩阵也是 `REFACTOR-REPORT.md` 要回答的三个问题之一
（「哪些模块失败会降级到什么程度」，任务书 §41.5、`AI_POLICY.md` §6）。
