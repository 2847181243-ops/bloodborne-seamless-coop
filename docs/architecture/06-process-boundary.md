# 进程边界规格（v2.0 新增，Human Owner 裁定）

> **这份文档回答一个问题**：哪些模块在游戏进程内，哪些在进程外，边界两侧怎么对话。
>
> **它是 Human Owner 在 2026-10 明确裁定的结果**，不是推导出来的默认值。
> 后续 T-005 / T-009 / T-012 / T-013 / T-021 都以它为前提。
>
> 如果你在读这份文档时发现某处与本文件冲突，**以本文件为准**并开 Issue 修正。

## 1. 决策

| 位置 | 内容 | 数量 |
|---|---|---|
| **游戏进程内** | Kernel、`mod.game_hook`、`mod.replication_core`、`mod.join_leave`、`mod.area_sync`、`mod.death`、`mod.world_reset`、`mod.enemy_boss`、`mod.loot`、`mod.pvp`、`mod.save` | 11 |
| **进程外**（辅助进程） | `mod.transport`、`mod.discovery`、`mod.relay`、`mod.crypto`、`mod.session_core`、`mod.observability` | 6 |

```text
游戏进程                              辅助进程
├─ Kernel                            ├─ mod.transport
├─ mod.game_hook                     ├─ mod.discovery
├─ mod.replication_core              ├─ mod.relay
├─ mod.join_leave                    ├─ mod.crypto
├─ mod.area_sync                     ├─ mod.session_core
├─ mod.death                         └─ mod.observability
├─ mod.world_reset
├─ mod.enemy_boss                         ↑
├─ mod.loot                               │
├─ mod.pvp                                │
├─ mod.save                               │
└─ mod.security_audit                     │
         ↑                                │
         └──────── IPC 边界 ──────────────┘
```

**分层与进程边界不是同一条线**：Layer 0 的五个模块刚好都在进程外，
但 `mod.observability` 是贯穿性辅助模块，它也在进程外；
`mod.security_audit` 留在进程内（它要审计进程内的行为）。

## 2. 为什么是这条分割线

**不是"核心与非核心"的划分，是操作系统的限制。**

### 2.1 挂钩子必须进程内

`mod.game_hook` 的工作是修改游戏自己的内存——往游戏的代码里写入跳转指令。
**操作系统禁止一个进程写另一个进程的内存**，所以这件事只能在游戏进程内部做。
没有绕过的办法。

### 2.2 读游戏数据必须进程内

以下数据全部位于游戏进程的地址空间里，进程外读不到：

| 数据 | 由谁使用 |
|---|---|
| 实体状态（敌人血量、位置、标志） | `mod.enemy_boss`、`mod.replication_core` |
| 玩家状态（HP、状态标志、死亡标记） | `mod.death`、`mod.replication_core` |
| 世界状态（Lantern 是否点亮、Boss 是否已击杀） | `mod.world_reset`、`mod.join_leave` |
| 库存与掉落 | `mod.loot` |
| 存档结构 | `mod.save` |
| 区域与场景状态 | `mod.area_sync` |
| 战斗判定 | `mod.pvp` |

### 2.3 曾考虑过、但被否决的做法

**把"逻辑"搬出去、"读内存"留在里面。**

否决理由：**崩溃恰恰发生在读内存那一步**。
内存访问留在哪个进程，崩溃风险就在哪个进程。
搬走逻辑只会增加 IPC 成本，**不减少任何风险**。

### 2.4 所以能搬出去的只有不碰游戏内存的模块

Layer 0 的五个模块做的是纯粹的 socket / 加密 / 状态机，完全不碰游戏内存；
`mod.observability` 只写日志。它们可以整体搬到另一个进程。

---

## 3. 为什么值得搬：真实的收益

**Layer 0 处理不受信任的网络输入。**

这是整个项目里最容易崩的地方，也是攻击面最大的地方：

- 畸形包
- 长度字段与实际不符
- 协议状态机被绕乱
- 解密前的数据解析
- 对端发来的、我们无法控制的任何东西

把这些代码隔离到另一个进程之后：**一个畸形包炸掉的是辅助进程，不是游戏。**

游戏进程能活下来，Kernel 检测到辅助进程退出，把 Layer 0 的模块标为不可用，
玩家至少还能单机继续，并看到明确的原因。

**这是这个决定唯一的收益，但它是真的。**

---

## 4. 代价：跨边界调用慢约一千倍

| | 量级 |
|---|---|
| 进程内函数调用 | 几纳秒 |
| 跨进程调用（共享内存 + 事件通知） | 几微秒到几十微秒 |

**这直接推出三条使用规则，它们是硬约束不是建议：**

### 4.1 不能每包一次跨边界调用

发送必须批量。Kernel 在辅助进程侧维护发送缓冲，
按帧或按固定间隔一次性提交，而不是每次 `send()` 都跨一次边界。

### 4.2 不能每帧查询跨边界状态

`ITransport::rtt_ms()`、`ISession::member_count()` 这类查询
在游戏进程侧**必须有本地缓存**，由辅助进程定期推送更新。
每帧查一次会把预算花光。

### 4.3 禁止每帧每实体一次跨边界调用

`mod.replication_core` 在进程内，所以它访问实体不需要跨边界。
但任何从进程内调用 Layer 0 的路径，都不得按实体数量做循环调用。

**判定标准**：如果一条路径的跨边界调用次数与"实体数 × 帧数"成正比，它就是错的。

## 5. 辅助进程的权限边界（Human Owner 裁定）

**辅助进程只有网络权限，零文件权限。**

这不是保守，是**这个决定存在的意义**。如果辅助进程能读写文件，那么：

```text
对端发一个畸形包
  -> 解析代码越界 -> 攻击者控制辅助进程
  -> 它能写文件 -> 可以改存档、改配置、植入可执行文件
```

把 Layer 0 搬出去、却不同时关掉文件权限，**只是搬走了一个进程，没有缩小爆炸半径**。

关掉之后：

```text
对端发一个畸形包
  -> 辅助进程被控制
  -> 但它没有任何文件句柄 -> 只能在内存里为所欲为
  -> IPC 断开，游戏进程发现并降级
  -> 磁盘上的东西（含原版存档 .sl2）全都碰不到
```

### 5.1 逐项核对它到底需不需要文件权限

| 事情 | 需要文件权限？ |
|---|---|
| 收发 UDP/TCP 包 | 不需要，网络权限 |
| 加密、握手、会话状态机 | 不需要，纯内存 |
| 记录日志 | **不需要** —— 见 §5.2 |
| 读取配置（`config/modules.yaml`） | **不需要** —— 启动时由 Kernel 经 IPC 下发 |
| 存档（`.bloodco`） | 不需要 —— `mod.save` 在进程内 |
| 原版存档（`.sl2`） | **绝对不需要** |

**结论：一样都不需要。**

### 5.2 日志必须经 IPC 回传

任务书 §34 要求日志异步写入。实现方式有两种，选第二种：

| 做法 | 后果 |
|---|---|
| 辅助进程自己写日志文件 | 需要写权限 —— 破口 |
| **辅助进程把日志记录经 IPC 送回，由游戏进程写** | **零文件权限** |

第二种顺带解决两件事：日志天然按时间顺序合并成一份；游戏进程本来就有文件权限（要写存档），多写一份日志不扩大攻击面。

**代价**：辅助进程崩溃时，管道里最后几条日志可能丢失。可接受 ——
辅助进程崩溃本身就是被记录的事件，游戏进程知道它什么时候断的。

**这条直接约束 T-021**：IPC 协议必须包含「日志记录回传」这一路消息，且每条记录要带「可丢 / 不可丢」类别 —— 诊断可丢并计数，审计类不静默丢（K-7 裁决，先例见 REF-002）。
不提前说，T-021 会按「辅助进程自己写日志」设计，之后改就要动协议。

**落盘归属（K-7 裁决，2026-10）**：游戏进程侧由 **Kernel 的日志设施**接收并写盘 —— 它 always-on，`[SECURITY]` 等强制日志不依赖 `mod.observability` 的存活；`mod.observability` 保持整体在进程外，负责记录内容、级别、聚合与上报策略。依据见 `docs/references/prior-art-log-pipeline.md`。

### 5.3 怎么强制（主防线与加固要分清）

**主防线是代码层面**：辅助进程**一行文件操作都不写**。

**进程层面是加固，不能反过来**：

- Windows：受限令牌或 AppContainer 启动辅助进程；至少不要给它任何文件路径参数
- Linux：seccomp 过滤 `open` / `openat`

⚠️ **Windows 上"彻底禁止文件访问"不如 Linux 干净。** AppContainer 能做到，
但它有自己的限制（例如网络访问需要额外声明能力）。
**所以代码层面那条是主防线**，进程层面只是加固。

### 5.4 可判定的验收

```text
1. kill 掉辅助进程
2. 断言游戏进程仍存活、自检报告 Layer 0 全部 Unavailable
3. 断言游戏进程的日志里**能找到辅助进程崩溃前记录的事件**
   —— 这同时证明了两件事：日志确实走了 IPC；辅助进程确实没自己写文件
```

第 3 条是这一节的关键：它把「零文件权限」从声明变成了可核对的证据。

### 5.5 这条约束归属谁

它是**安全架构约束**，按 `MAINTAINERS.md` §6 属 `docs/security/` 的范围，
应由 AI-C2 补进 `constraints.md`（现有 C-001…C-019）。

**Human Owner 已裁定其内容**，AI-C2 的工作是把它与既有 19 条对齐
（尤其核对 C-016 引用的任务书 §34 是否涉及日志文件归属），并给出编号。

## 6. 全局 Gate 第 9 项的诚实表述

任务书写的原文是：

> 任一非核心模块崩溃 → 进程存活，其他模块继续工作

**采用进程边界之后，这条只对进程外的模块成立。**

| 崩溃的模块 | 结果 | 能否避免 |
|---|---|---|
| 进程外的 6 个 | ✅ 游戏进程存活，那部分功能降级 | 可以，已由进程隔离保证 |
| 进程内的 11 个 | ❌ **游戏进程退出** | **不能**，这是操作系统层面的限制 |

**必须如实记录这一点，不得声称"Gate 第 9 项已满足"。**

进程内的模块仍然做进程内隔离（错误码、异常捕获、`tick` 超时熔断），
它能把"模块报告失败"变成"该模块不可用而其余继续"，
**但挡不住段错误**。

### 6.1 这条限制对 T-018 的影响

T-018 的九项全局 Gate 里第 9 项需要改写为可判定的形式：

```text
原表述：任一非核心模块崩溃 → 进程存活
可判定形式（建议）：
  scripts/run_process_isolation.sh
    1. kill 辅助进程
    2. 断言游戏进程仍存活、且自检报告 Layer 0 全部 Unavailable
    3. 退出码 0
  进程内的模块：
    单独用「tick 抛异常 / 返回错误」注入，断言该模块变为 Unavailable
    且其余模块仍为 Ok；**不注入段错误**（无法在进程内恢复）
```

最终形式由 T-012 / T-013 确定，本节只固定"必须区分这两类"。

## 7. 对已冻结的接口层（v1）的影响

**结论：`src/interfaces/` 下的 7 个头文件不需要修改。**

理由：调用方拿到的仍然是一个 `ITransport*`，只是那个指针指向**本地代理**，
代理负责序列化并把调用送过边界。**模块在哪个进程，对调用方透明。**

```text
进程内调用方
  auto* t = find_service<ITransport>(*ctx.host);   // 不变
  t->send(buf, len);                                // 不变

  └─ 指针实际指向 TransportProxy（本地对象）
       └─ 序列化 → 共享内存 → 事件通知 → 辅助进程的真实实现
```

这是接口层按纯虚接口设计带来的直接好处：**它是位置无关的。**

### 7.1 但接口层的实现方式要增加一层

T-021 需要产出：

1. **IPC 传输**：共享内存环形缓冲 + 控制通道（不要每次调用一次系统调用）
2. **代理与桩**：每个跨边界的能力接口各一份（`ITransport` / `ISession`；
   `IGameplay` 只在进程内使用，不需要代理）
3. **可跨边界的类型**：现在只有 `Error`、`Health`、`const char*`、定长整数
   与 `span<const uint8_t>` 这类 POD；**指针与引用一律不可跨边界**

### 7.2 一个必须现在就注意的约束

`module_context.h` 里的 `find_service<T>()` 返回裸指针，**不可跨边界**。
所以：

- **辅助进程内的模块不能用 `find_service` 找别的进程的模块**；
  它们之间的依赖由 IPC 层解析，而不是由指针传递。
- 这一点在 T-021 的定义里必须写清楚，否则第一个进程外模块就会踩。

## 8. 这个决定不会锁死未来

进程边界是**可调整的**：

- 把某个模块从进程内移到进程外，或反过来，**不需要改任何调用方代码**
  （因为接口位置无关，代理是实现细节）。
- 唯一需要改的是 IPC 层的路由表与序列化支持。

**这也是为什么现在必须把它定下来**：它决定 Kernel 是不是要给远程代理当宿主、
决定 CMake 目标是否需要分成两个可执行文件、
决定 T-012 的 module-isolation 要不要跨越进程边界。
这些一旦建起来再改，成本远高于现在。
