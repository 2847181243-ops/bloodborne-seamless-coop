# Kernel 的职责与边界

这份文档回答一个问题：Kernel 做什么，以及**不做什么**。
任务书说 Kernel「不含任何业务逻辑」（任务书 §3.6 原则 1），
这份文档把这个说法拆成可以检查的条目：哪些事必须由 Kernel 做，哪些事一旦出现在 Kernel 里就是越界。

---

## 1. Kernel 在系统中的位置

- Kernel 是运行时的宿主，**不计入 15 个模块**（任务书 §3.6）。
- Kernel 失败时**不加载 Mod，原版启动**（任务书 §3.6 注册表 Kernel 行、§3.7 分层表）。
- Kernel 负责加载模块、维持模块的健康状态、在模块失效时停用该模块；
  模块负责具体的联机与游戏功能（任务书 §3.6 原则 1 与原则 2）。
- Kernel 与 `src/interfaces/`（冻结的 v1 接口）一起，对应任务书 §41.4 中的
  `src/kernel/` 与 `src/interfaces/` 两个目录。

---

## 2. Kernel 必须做的六件事

任务书 §3.6 原则 1 列出六项职责，任务书 §41.1 T-005 给出对应的验收点。

| 职责 | 内容 | 依据 |
|---|---|---|
| 加载 | 加载模块，读取模块注册与配置。`init` 失败不得阻断其他模块 | 任务书 §3.6 原则 1、§41.1 T-005 |
| 配置 | 读取 `config/modules.yaml`、`config/features.yaml`（配置文件本身由 T-008 产出）。未知模块 ID 拒绝启动 | 任务书 §3.6 原则 1、§41.1 T-008 |
| 日志 | Kernel 自身与模块加载过程的日志 | 任务书 §3.6 原则 1 |
| 事件总线 | 模块之间的消息通过事件总线投递 | 任务书 §3.6 原则 1 |
| 健康巡检 | 周期性取得各模块的健康状态并汇总 | 任务书 §3.6 原则 1、§41.1 T-006（覆盖健康聚合） |
| 熔断 | 模块 `tick` 超时后熔断；把失效模块标记为不可用 | 任务书 §3.6 原则 1、§41.1 T-005 |

配套产出（属于 T-005 / T-006，不改变 Kernel 的职责范围）：

- 可执行宿主 `bloodcoop-host`（任务书 §41.1 T-005、§41.4）。
- `bloodcoop-host --self-test` 输出 JSON；required 项失败时退出码非 0（任务书 §41.1 T-014）。
- Kernel 单元测试：3 个测试夹具 + 4 个单元测试，覆盖加载、故障隔离、熔断、健康聚合
  （任务书 §41.1 T-006）。

Kernel 六项职责的具体接口签名、阈值、周期与状态取值，任务书都没有给出 → 见第 6 节。

## 3. Kernel 不做什么

「不含任何业务逻辑」（任务书 §3.6 原则 1）在实施中要落成下面这些可检查的条款。

### 3.1 不实现任何游戏机制

死亡与重生、世界重置、敌人与 Boss 状态、掉落与库存、PvP 结算、存档写入
都不在 Kernel 内。它们的职责归属见任务书 §3.6 注册表：
`mod.death`、`mod.world_reset`、`mod.enemy_boss`、`mod.loot`、`mod.pvp`、`mod.save`。

任务书 附录 B 明确写了：v2.0 只规定了模块边界，没有规定模块内部该做什么；
§9–§25 的游戏机制设计仍然有效。这些机制落在 §3.6 注册表对应的模块里，不上收到 Kernel。

### 3.2 不持有业务数据

玩家状态、世界状态、存档数据、掉落归属、PvP 结算结果都不属于 Kernel。
Kernel 的职责清单（任务书 §3.6 原则 1）里没有这些条目，
它们分别属于 `mod.session_core`、`mod.replication_core`、`mod.save`、`mod.loot`、`mod.pvp`。

### 3.3 不做 Hook、不做密码学、不做传输

- Hook 与地址解析属于 `mod.game_hook`（任务书 §3.6 注册表；附录 A 把原 AI-A1 的
  `mod/core/` 映射到 `mod.game_hook`）。
- 握手、加密、认证属于 `mod.crypto`（任务书 §3.6 注册表；§45.2 密码学方案）。
- UDP/TCP/中继传输与连接生命周期属于 `mod.transport`（任务书 §3.6 注册表）。

### 3.4 不代替模块决定降级行为

每个模块有**独立的健康状态与独立的降级路径**（任务书 §3.6 原则 2）。
Kernel 的权限到「把模块标记为不可用（熔断）」为止；
该模块不可用时对外表现成什么样，由模块自己的降级路径决定，
并写进 [04-degradation-matrix.md](04-degradation-matrix.md)。

> 这条分界是**由 §3.6 原则 1 与原则 2 推出**的：原则 1 把业务逻辑排除在 Kernel 之外，
> 原则 2 把降级路径交给模块。任务书没有单独写一句话说明这条分界，
> 若将来要把某类降级决策放进 Kernel，需要按 `AI_POLICY.md` §3 建 Issue 问人。

### 3.5 不提供安全降级路径

Kernel 不得为 `mod.crypto` 失败提供「先用明文连上再说」的通道，
也不得为反作弊失败提供「继续 PvP」的通道（任务书 §3.6 原则 6；
`MAINTAINERS.md` §3 第 1 条；`AI_POLICY.md` §2.1 第 1 条；
`docs/security/constraints.md` C-001）。

## 4. Kernel 失败时会怎样

| 场景 | 行为 | 依据 |
|---|---|---|
| Kernel 在游戏进程内初始化失败 | 不加载 Mod，原版启动 | 任务书 §3.6 注册表、§3.7 分层表 |
| `bloodcoop-host --self-test` 的 required 项失败 | 退出码非 0（供 CI 判定） | 任务书 §41.1 T-014 |
| 某个模块加载失败 | 不阻断其他模块继续初始化 | 任务书 §41.1 T-005 |

「核心模块」与「非核心模块」的划分任务书没有列出（任务书在 §3.6 原则 5、
§41.3 全局 Gate 9 中使用了「非核心模块」这个词，但没有给清单）→
**待定：核心模块清单需要裁决**，见 [00-overview.md](00-overview.md) 第 7 节 O-1。
在裁决之前，Kernel 的失败行为只按任务书 §3.6 注册表那一行执行（失败则不加载 Mod）。

## 5. Kernel 边界的可判定项

| 检查项 | 判定方式 | 通过条件 | 依据 |
|---|---|---|---|
| Kernel 不依赖任何模块 | 删除任意一个模块目录后，`bloodcoop-host` 仍可构建 | 构建退出码 0 | 任务书 §41.1 T-009（「删除单模块后其余仍可构建」） |
| 模块间非法链接被拒绝 | CMake 配置阶段拒绝模块 target 之间的链接 | 配置退出码非 0 | 任务书 §41.1 T-009 |
| 单个模块 `init` 失败不影响其他模块 | 故障注入：让一个模块 `init` 返回失败，其余模块完成初始化 | 断言失败即退出码非 0 | 任务书 §41.1 T-005、T-013 |
| `tick` 超时熔断 | 注入一个不返回的模块，Kernel 在超时后把该模块标记为不可用 | 断言失败即退出码非 0 | 任务书 §41.1 T-005 |
| 健康状态聚合正确 | Kernel 单元测试（4 个用例覆盖加载、故障隔离、熔断、健康聚合） | 测试退出码 0 | 任务书 §41.1 T-006 |
| 自检汇总可用 | `bloodcoop-host --self-test` 输出 JSON，`overall` 字段为 `pass` | 退出码 0；required 失败非 0 | 任务书 §3.7 全局 Gate 6、§41.1 T-014 |
| Kernel 内无业务逻辑 | 代码审计：确认 Kernel 中不存在死亡 / 世界重置 / 敌人 / 掉落 / PvP / 存档机制的实现 | 人工审计结论 | 任务书 §3.6 原则 1（审计方式与判据由 T-006 落地） |

上表中「非法链接被拒绝」「删除单模块后仍可构建」两条的判定脚本，
任务书 §41.4 没有列出（那里只列了 `self_test.sh`、`run_fault_injection.sh`、
`run_module_isolation.sh`、`package.sh`）→
**待定：脚本名由 T-009 / T-012 确定**。

## 6. 待定事项

| 编号 | 待定内容 | 缺什么 | 由谁决定 |
|---|---|---|---|
| K-1 | `tick` 超时的具体毫秒阈值 | 任务书只写「`tick` 超时熔断」，没有给数值 | T-005 |
| K-2 | 健康巡检周期 | 任务书只写「健康巡检」，没有给周期 | T-005 |
| K-3 | 熔断后的恢复策略（是否自动恢复、退避、是否需要重启） | 任务书没有写 | T-005 |
| K-4 | 模块健康状态的取值集合 | 任务书只在 T-007 出现过一个状态值 `Unavailable`（模块的初始实现默认返回它且不崩溃）；完整枚举未给 | T-004 / T-005 |
| K-5 | 模块是运行时动态加载还是静态链接 | 任务书只给了 CMake target 结构（T-009），没有规定加载方式 | T-005 / T-009 |
| K-6 | 模块崩溃如何被 Kernel 捕获 | 任务书承诺「任一非核心模块崩溃，进程存活」（§3.6 原则 5），但没有规定模块与 Kernel 是否在同一进程内、进程内崩溃如何被隔离与捕获 | T-005（这是该承诺能否成立的前提，见 [03-fault-isolation.md](03-fault-isolation.md) 第 6 节） |
| K-7 | Kernel 的日志职责与 `mod.observability` 的分工 | 任务书 §3.6 原则 1 把「日志」列为 Kernel 职责，注册表又把 `mod.observability` 定义为「日志 / 指标」，两者边界未写 | T-004 / T-005 |
| K-8 | 事件总线的投递语义（同步或异步、是否允许阻塞、重入规则） | 任务书只写「事件总线」，没有规定语义 | T-004 / T-005 |
| K-9 | `--self-test` 的 JSON 字段结构 | 任务书只给了 `overall: pass` 一个字段和「required 失败退出码非 0」 | T-014 |
| K-10 | `src/platform/` 与 Kernel 的分工 | 任务书附录 A 只说明它不在 15 个模块内 | 需要裁决 |

Kernel 的日志、事件总线、配置读取都必须遵守 `docs/security/constraints.md` C-016：
任何日志（含调试日志）不得记录 IP、平台账号 ID、硬件指纹、设备信息、地理位置或任何可追踪标识。
