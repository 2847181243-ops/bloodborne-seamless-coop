# 故障隔离

这份文档回答两个问题：故障怎么被限制在模块内、Kernel 如何检测与熔断；
以及任务书里那些自然语言写成的层出口条件，如何变成有退出码的判定项。

---

## 1. 三条已确定的规则

1. **模块即故障边界。** 每个模块有独立的模块 ID、独立的构建目标、独立的测试、
   独立的健康状态、独立的降级路径（任务书 §3.6 原则 2）。
2. **故障不传播。** 任一非核心模块崩溃，进程存活，其他模块继续工作
   （任务书 §3.6 原则 5）。这一条同时是发布前的全局 Gate 第 9 项（任务书 §3.7、§41.3）。
3. **安全硬依赖是唯一的例外。** `mod.crypto` 失败时拒绝联机，**不降级为明文**；
   反作弊失败时仅禁用 PvP（任务书 §3.6 原则 6）。

第 3 条仍然属于故障隔离，只是结果不同：加密模块不可用时，系统不切换到别的连接方式，
而是直接拒绝联机。

---

## 2. Kernel 如何检测模块失效

| 时机 | 检测方式 | 依据 | 状态 |
|---|---|---|---|
| 加载期 | 模块 `init` 返回失败 → Kernel 记录该模块不可用，继续初始化其他模块 | 任务书 §41.1 T-005 验收「`init` 失败不阻断其他模块」 | 已确定 |
| 运行期 | 模块 `tick` 超时 → 熔断 | 任务书 §41.1 T-005 验收「`tick` 超时熔断」 | 阈值待定（F-1） |
| 运行期 | 健康巡检取得各模块健康状态并汇总 | 任务书 §3.6 原则 1、§41.1 T-006 | 周期与状态取值待定（F-1 / K-4） |
| 运行期 | 模块进程内崩溃 | 任务书 §3.6 原则 5 承诺「进程存活」 | 捕获机制待定（F-2） |
| 消息级 | 校验失败（HMAC / 序列号 / 版本 / 指纹）→ 记 `[SECURITY]` 日志并拒绝该消息 | `docs/security/constraints.md` C-007 | 已确定 |

最后一行与前四行不是同一类：它拒绝的是**一条消息**，不是停用一个模块。
两者的日志与判据必须分开，不能把「消息被拒」当成「模块失效」。

---

## 3. 熔断之后发生什么

- Kernel 把失效模块**标记为不可用**；其他模块继续运行（任务书 §3.6 原则 5）。
- 该模块不可用时对外表现成什么样，由**模块自己的降级路径**决定
  （任务书 §3.6 原则 2），矩阵见 [04-degradation-matrix.md](04-degradation-matrix.md)。
- **熔断不得成为绕过安全约束的手段。** `mod.crypto` 被熔断时不得启用明文通道
  （任务书 §3.6 原则 6；`docs/security/constraints.md` C-001；
  `MAINTAINERS.md` §3 第 1 条）。任何以「模块已经停了」为由放开安全限制的实现都违反硬性禁止。
- 熔断后是否自动恢复、如何退避、是否需要重启 → **待定**（F-3）。

隔离效果的判定方式（任务书 §41.1 T-012）：
`module-isolation` workflow 逐个禁用非核心模块，并断言自检退出码为 0。
CI 的五个 workflow 是 `build` / `test-unit` / `test-contract` / `fault-injection` /
`module-isolation`（任务书 §41.1 T-012）。
仓库当前只有 `.github/workflows/build.yml`；`test-unit` / `test-contract` /
`fault-injection` / `module-isolation` 四个 workflow 尚不存在，它们是 T-012 的产出。
本节给出的是它们应当满足的判定形式。

## 4. 层出口条件转成可判定项

任务书明确指出：层出口条件目前是自然语言，实施时**必须转成可判定项（脚本 + 退出码）**，
否则只能靠人说「我觉得可以了」（任务书 §3.7 与 §41.3 两处都写了这句话）。

本节把三条层出口条件与九项全局 Gate 逐条转写。
**凡任务书没有给出的阈值，一律标「待定」并写出决定方，不填看起来合理的数字。**

### 4.1 Layer 0

```text
条件原文：bloodcoop-net CLI 可完成房间码连接、双向收发、断线重连，30 分钟稳定
           （任务书 §3.7；§41.3 写作「稳定 30 分钟」，是同一条件）

判定方式：scripts/run_layer0_soak.sh（脚本名待定，见下）
          分为四段，任一段失败即整体退出码 1：
          1) 连接：两端用房间码建立连接，连接成功则进入下一段
          2) 双向收发：两端互相发送报文并校验回显一致
          3) 断线重连：断开一端，另一端在会话保留窗口内恢复；窗口为 30~60 秒
             （任务书 §29.4）
          4) 稳定性：连续运行 30 分钟，期间周期性采样延迟与丢包率；
             延迟 > 500ms 或丢包率 ≥ 5% 判失败（阈值来源：任务书 §36 性能预算）
          四段全部通过 → 退出码 0；任一段失败 → 退出码 1

退出码语义：0 = 层出口条件达标；1 = 未达标；其余非 0 = 脚本自身执行失败（环境问题）

阈值来源：30 分钟来自任务书 §3.7 / §41.3；延迟与丢包阈值来自任务书 §36
          （「最大延迟：500ms」「最大丢包率：< 5%」）

待定：采样间隔未给出（任务书没有规定多久采样一次）→ 由 T-012 决定
待定：脚本名。任务书 §41.4 列出的脚本只有 scripts/self_test.sh、
      run_fault_injection.sh、run_module_isolation.sh、package.sh，
      **没有层出口脚本** → 名称与落地任务由 T-012 / T-013 决定
```

### 4.2 Layer 1

```text
条件原文：双人游戏内互相可见、可移动、可切换区域，客机加入不触发原版召唤
           （任务书 §3.7、§41.3）

判定方式：这条**无法只用脚本判定**。可机器判定的部分与只能人工判定的部分必须分开：

          机器部分（脚本退出码）：
          a) 两名玩家的游戏进程在测试期间未崩溃
          b) bloodcoop-host --self-test 返回 0（任务书 §41.1 T-014）
          c) 各模块契约测试通过（任务书 §41.1 T-007 的 tests/contract_test.cpp）
          d) 日志中出现「客机已加入」「区域切换已同步」的既定标记

          人工部分：
          e) 双人游戏内互相可见
          f) 双人可移动
          g) 可切换区域
          h) 客机加入不触发原版召唤

退出码语义：0 = 机器部分全部通过；非 0 = 机器部分失败。
          机器部分通过**不等于**层出口条件达成，人工部分必须另行判定。

阈值来源：无（本条件不含数值阈值）

说明：机器部分 a) 与 d) 是为判定新增的断言，不是层出口条件的原文；
      e) 到 h) 逐字对应条件原文。

待定：d) 所需的日志前缀与字段。任务书 §34 给了日志前缀清单，
      但没有规定「客机加入」「区域切换同步」用什么前缀、哪些字段 → 由 T-007 / T-012 决定
待定：人工部分由谁执行、以什么证据留痕。任务书 §41.6 第 5 条要求 T-018 报告附原始命令输出；
      层出口条件是否达标由 Human Owner 裁决（MAINTAINERS.md §7）
```

### 4.3 Layer 2

```text
条件原文：完整 Session 可完成一个区域；任一 L2 模块禁用不影响其他模块与 P2P
           （任务书 §3.7、§41.3）

判定方式：这条有两个必须分别判定的部分。

          可机器判定部分：「任一 L2 模块禁用不影响其他模块与 P2P」
          scripts/run_module_isolation.sh（任务书 §41.4 已列出该脚本）
          逐个禁用 6 个 Layer 2 模块（mod.death、mod.world_reset、mod.enemy_boss、
          mod.loot、mod.pvp、mod.save，见任务书 §3.6），每禁用一次断言：
          a) bloodcoop-host --self-test 退出码为 0（任务书 §41.1 T-012 原文：
             「module-isolation 逐个禁用非核心模块并断言自检退出码 0」）
          b) P2P 连接仍可建立（Layer 0 的收发判定仍通过）
          6 个用例全部通过 → 退出码 0；任一用例失败 → 退出码 1

          只能人工判定部分：「完整 Session 可完成一个区域」
          需要真实游戏流程（两名玩家、真实区域、真实 Boss 或区域结束条件）
          → 人工判定 + 证据留痕

待定：T-012 的规则写的是「逐个禁用非核心模块」，而核心模块清单任务书没有给出
      （见 [00-overview.md](00-overview.md) O-1）→ T-012 落地前需要先裁决；
      在裁决之前，本判定按「6 个 L2 模块全部逐个禁用」执行
待定：L2 全禁用模拟的运行时长门槛。任务书 §41.1 T-013 写「L2 全禁用模拟运行 ≥30 分钟」，
      但这是故障注入套件的验收，不是 Layer 2 出口条件的原文
```

### 4.4 全局 Gate 九项

任务书 §3.7 与 §41.3 是同一份清单，两处必须同时改（任务书 §41.3 原文）。

| 项 | 内容（任务书 §41.3） | 判定方式 | 退出码 |
|---|---|---|---|
| 1 | 全量构建成功 | `build` workflow：MSVC x64 构建（`docs/standards/build-standards.md` §1） | 0 = 成功 |
| 2 | 全量单元测试通过 | `test-unit` workflow | 0 = 通过 |
| 3 | 全量契约测试通过 | `test-contract` workflow | 0 = 通过 |
| 4 | 故障注入全部通过 | `fault-injection` workflow；`scripts/run_fault_injection.sh`（任务书 §41.4） | 0 = 全部通过 |
| 5 | 模块隔离全部通过 | `module-isolation` workflow；`scripts/run_module_isolation.sh`（任务书 §41.4） | 0 = 全部通过 |
| 6 | `--self-test` 输出 `overall: pass` | `bloodcoop-host --self-test` 输出 JSON，解析 `overall` 字段 | 0 = `pass`；required 失败非 0（任务书 §41.1 T-014） |
| 7 | 禁用全部 L2 模块后游戏单机 30 分钟无崩溃 | 见下方补充 | 见下方补充 |
| 8 | `crypto` 失败 → 拒绝联机，不降级明文 | 故障注入 `crypto fail` 用例（任务书 §41.1 T-013）：断言联机被拒绝；并配合代码审计确认不存在明文路径（`docs/security/constraints.md` C-001） | 0 = 行为符合预期 |
| 9 | 任一非核心模块崩溃 → 进程存活，其他模块继续工作 | 故障注入 `kill` 用例（任务书 §41.1 T-013）：断言宿主进程仍存活，且随后 `--self-test` 仍返回 0 | 0 = 行为符合预期 |

第 7 项的补充：

```text
判定方式：需要「禁用全部 L2 模块后运行 30 分钟」的模拟或真实运行，
          断言期间无崩溃（进程存活、无崩溃日志）。
          该用例由 scripts/run_fault_injection.sh 承载（任务书 §41.4 列出了该脚本）：
          任务书 §41.1 T-013 的故障注入套件包含「L2 全禁用」，
          并要求「L2 全禁用模拟运行 ≥30 分钟」。

待定：「模拟运行」是否允许在无游戏进程的环境下判定，还是必须跑真实游戏进程。
      任务书用了「模拟」二字，但没有说明模拟的边界 → 由 T-013 决定。
      若必须跑真实游戏进程，还需要明确崩溃的判定方式（进程退出码、看门狗还是日志）
      → 由 T-013 决定。
```

### 4.5 判定项汇总的落地要求

- 每个判定脚本必须给出**退出码语义**，不能只给出日志。
- 无法自动化的判定项必须逐个列出**具体技术原因**（缺哪类依赖、缺哪个系统能力），
  不能写「无法测试」（任务书 §52-d）。
- T-018 的报告必须附**原始命令输出**，不得只写结论（任务书 §41.6 第 5 条）。

## 5. 故障注入套件

任务书 §41.1 T-013 规定的用例类别：

| 用例类别 | 断言对象 |
|---|---|
| `kill` | 模块被杀后进程存活，其他模块继续工作（全局 Gate 9） |
| `timeout` | `tick` 超时后熔断（阈值见 F-1） |
| `crypto fail` | 拒绝联机，不降级明文（全局 Gate 8） |
| `hook fail` | Hook 失败必须明确记录日志、不允许静默失败（任务书 §5.5） |
| `L2 全禁用` | 运行 ≥30 分钟（任务书 §41.1 T-013） |

要求（任务书 §52-d）：每个用例有明确断言，不是「跑一下看看」；
断言的真实输出写进 `REFACTOR-REPORT.md`。

| I-4 | `mod.observability` 失效与 C-007 的日志义务冲突 | C-007 要求任何校验失败必须记录 `[SECURITY]` 日志；若日志由 `mod.observability` 承载，则该模块失效时 C-007 无法满足。C-007 是强制条款，违反后果为 FAIL | 待定：需要裁决（安全优先，裁决方 AI-C3，任务书 §49） |

| I-6 | `mod.save` 失效与 C-018 的关系 | C-018 要求所有存档写入原子化、只写入来源合法的物品，违反后果为 FAIL。任务书没有写存档模块失效时是否允许继续联机 | 待定：需要裁决（安全优先，裁决方 AI-C3，任务书 §49） |
| I-7 | `mod.relay` 失效与信誉筛选的关系 | `docs/interfaces/b3_to_b4_reputation.md` 要求 `isEligible` 判定失败时拒绝该节点（fail-closed），且「全部候选不合格 → 返回空列表，不得降级到无信誉校验的节点」。任务书 §3.6 的模块注册表里没有独立信誉模块（附录 A 说信誉并入 `mod.session_core` / `mod.discovery`） | 待定：信誉逻辑归属模块未定（见 [04-degradation-matrix.md](04-degradation-matrix.md) 第 5 节） |

## 7. 更新义务

出现下列任一情况时，必须同步更新故障注入套件与降级矩阵（任务书 §52-d）：

- 新增一个模块；
- 一个模块新增对外的依赖；
- 一个模块的失败行为发生变化；
- 新增一类失败场景。

同时，层出口条件未通过时不得合并上层模块、模块 Gate 未通过时不得合并该模块的后续改动
（任务书 §52-b）。
「CI 全绿」与这条规则不重复：CI 全绿只说明本 PR 自身没问题，不说明它所依赖的层已经达标
（任务书 §52-b）。
